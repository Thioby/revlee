# AI / agent-architecture patterns for an autonomous PR verification agent (state as of 2026-10-14)

Scope: design patterns, models, prompts and evaluation methods for an agent that reads a PR (diff + description + ticket), derives a verifiable test plan, drives a running app through a computer-use / GUI agent, judges outcomes, controls cost/flakiness, stays safe, and produces a trustworthy evidence report.

Research-access note for the report writer: in this environment arxiv.org, alphaxiv.org, export.arxiv.org, api.semanticscholar.org, momentic.ai, yutori.com, os-world.github.io, platform.openai.com, developers.openai.com, docs.stagehand.dev and midscenejs.com were blocked by the egress proxy (HTTP 403 / DNS failure), so facts about those sources come from search-result snippets rather than full-page reads. Anthropic's documentation (platform.claude.com, code.claude.com), GitHub raw files and GitHub-hosted READMEs were read in full. Where a number comes only from a snippet or from a third-party aggregator, this is stated.

## KQ1. GUI / computer-use agents: state of the art, perception, latency and cost (Oct 2026)

### Takeaway
By mid-2026 frontier computer-use agents exceed the ~72% human baseline on OSWorld-Verified (top official-workbook entries ~85–90%; Anthropic Claude 5-family ~85%, OpenAI GPT-5.4 75%), but the harder long-horizon OSWorld 2.0 is still far from solved (best full-completion rates 20–44% depending on track) and a single long task costs tens of dollars; AndroidWorld aggregators show ~85–87% for the best models (Qwen3.8 family, Sept 2026). Perception for mobile should be hybrid: accessibility tree first, screenshot/Set-of-Mark as fallback, with LLM latency (not device I/O) dominating per-step time.

**Latency and cost per step**
- OSWorld-Human (MLSys 2026 oral): planning and reflection LLM calls account for 75–94% of total latency; later steps are up to 3x slower than early ones as context grows; agents take 1.4–2.7x more steps than the human-annotated trajectory. — [OSWorld-Human](https://arxiv.org/html/2506.16042v1); [MLSys 2026 listing](https://mlsys.org/virtual/2026/oral/3865)
- Step-level optimization study (OSWorld, 2xH100 local deployment): per-request latency from ~2.6 s (EvoCUA-8B) to ~8.3 s (Kimi K2.5); estimated cost per task from ~$0.018 (Qwen3-VL-8B) to ~$0.881 (Claude Sonnet 4.5), accuracies ~31–60%; cascading a small model with a large one cut cost substantially (OpenRouter price estimates). — [arXiv 2604.27151 (snippet)](https://arxiv.org/pdf/2604.27151)
- UFO2 desktop AgentOS: ~10 s per step excluding LLM inference, ~1 s extra for visual parsing, ~1 minute per task after step reductions. — [UFO2 (snippet)](https://arxiv.org/pdf/2504.14603)
- Third-party practitioner comparison: Stagehand ~5–10 s per run, Browser Use ~15–30 s, raw Playwright <2 s; Browser Use "reasons from scratch on each run" giving a flatter cost curve than Stagehand's cache-driven one. — [TinyFish Current](https://current.tinyfish.ai/issue/latest/foundations/article/11665)

### Inferences
- For a PR verifier the relevant regime is short, well-specified flows (5–30 steps), not OSWorld-2.0-style 500-step tasks; at ~1,000–1,800 tokens per screenshot and Anthropic's batch-actions feature, a 20-step flow is on the order of 40–80k input tokens before caching, i.e. low single-digit dollars per scenario on a frontier model — consistent with the ~$0.9/task Sonnet 4.5 figure on OSWorld.
- Use a frontier model (Claude Sonnet 5.5/Fable 5.1-class, GPT-5.4-class) for planning/judging and a cheaper model or deterministic replay for execution; the cascade study and OSWorld-Human both indicate the LLM call is the bottleneck, so the fewer model-in-the-loop steps, the faster and cheaper.
- On mobile prefer a11y-tree-first with screenshot fallback (mobile-mcp's default) and SoM overlays only when labels are missing; the AndroidWorld data shows SoM helps grounding but the harness matters more than the model.

## KQ2. MCP as the integration layer; running the agent in GitHub Actions with read-only GitHub context plus a device tool

### Takeaway
Claude Code / the Claude Agent SDK and `claude-code-action` already provide the pattern: pass one or more MCP servers (GitHub for PR/issue context, a device/browser server for the app) via `--mcp-config` / `mcpServers`, and gate exactly which tools are callable with `--allowedTools` using `mcp__<server>__<tool>` names; read-only GitHub access is achieved by allowing only read tools and granting the workflow token `contents: read`/`pull-requests: read`. Fork PRs are the main hazard: never check out an untrusted head into the workspace root, and expect secrets to be withheld on public-repo fork PRs.

### Cited Findings
- `claude-code-action`: custom MCP servers are passed with `--mcp-config` inside `claude_args` and "merge with the built-in GitHub MCP servers"; inline JSON uses top-level `mcpServers` with `command`, `args`, `env`, `type` (e.g. `"type": "stdio"`); multiple `--mcp-config` flags merge and "your custom servers will override any built-in servers with the same name"; a repo-root `.mcp.json` is auto-detected but its tools still must be explicitly allowed; the action always sets `enableAllProjectMcpServers: true`. Secrets should be written to a file in a prior step (e.g. `/tmp/mcp-config.json`) and referenced as `${{ secrets.X }}`. — [claude-code-action configuration.md](https://raw.githubusercontent.com/anthropics/claude-code-action/main/docs/configuration.md)
- Tool gating: by default Claude has file operations, comment management and basic GitHub operations but no arbitrary Bash; add with `--allowedTools "Bash(npm run test),Edit,..."`, block with `--disallowedTools`; MCP tools follow `mcp__<server>__<tool>`; with `actions: read` the built-in CI tools are `mcp__github_ci__get_ci_status`, `mcp__github_ci__get_workflow_run_details`, `mcp__github_ci__download_job_log`; `--max-turns 5` limits iterations. — [claude-code-action configuration.md](https://raw.githubusercontent.com/anthropics/claude-code-action/main/docs/configuration.md)
- Official GitHub Actions docs: automation mode (a `prompt` is provided) runs on any event; "for a plain-text prompt, Claude has no shell or GitHub API access until you grant the tools the prompt needs"; the Code Review example runs with `permissions: contents: read, pull-requests: read, issues: read, id-token: write` and `claude_args: '--allowedTools "mcp__github_inline_comment__create_inline_comment"'`; "the Claude Code GitHub Action starts the MCP server that posts inline comments only when `--allowedTools` in `claude_args` names it"; the daily-report example allows `mcp__github__list_commits,mcp__github__list_issues` and omits checkout. — [Claude Code GitHub Actions docs](https://code.claude.com/docs/en/github-actions)
- "On public repositories, GitHub withholds secrets from runs triggered by fork pull requests, so the review runs only on pull requests from branches in the same repository." — [Claude Code GitHub Actions docs](https://code.claude.com/docs/en/github-actions)
- Cost controls listed by Anthropic: `--max-turns`, workflow-level timeouts, GitHub concurrency controls, concise `CLAUDE.md`; OIDC workload-identity federation (`anthropic_federation_rule_id`, `anthropic_organization_id`, `anthropic_service_account_id`, `anthropic_workspace_id`, needs `id-token: write`) avoids a long-lived API-key secret. — [Claude Code GitHub Actions docs](https://code.claude.com/docs/en/github-actions)
- Agent SDK: MCP servers configured in `options.mcpServers` (stdio `command/args/env`, `type: "http"`/`"sse"` with `url` and `headers`, or in-process SDK servers via `createSdkMcpServer()`); tools require explicit permission — "prefer `allowedTools` over permission modes for MCP access": `acceptEdits` does not auto-approve MCP tools and `bypassPermissions` disables most other prompts; wildcards like `mcp__github__*` are supported; GitHub remote server example uses `https://api.githubcopilot.com/mcp/` with `Authorization: Bearer ${GITHUB_TOKEN}` and `allowedTools: ["mcp__github__list_issues"]`. — [Agent SDK MCP docs](https://code.claude.com/docs/en/agent-sdk/mcp)
- Agent SDK init message reports each MCP server's `status` (`pending`/`connected`/`failed`/`needs-auth`/`disabled`); the SDK does not run interactive OAuth — pass tokens in headers; MCP output >25,000 tokens is spilled to a file; `MCP_TIMEOUT` default 30 s. — [Agent SDK MCP docs](https://code.claude.com/docs/en/agent-sdk/mcp)
- The read-only pattern is demonstrated in the SDK docs with DBHub: `readonly = true` makes the MCP server itself reject writes "so the example cannot modify your data even if the agent emits a write". — [Agent SDK MCP docs](https://code.claude.com/docs/en/agent-sdk/mcp)
- Headless/CI gotcha: bare `claude -p` mode skips OAuth/keychain so Anthropic auth must come from `ANTHROPIC_API_KEY` or an `apiKeyHelper`; MCP servers needing browser OAuth fail in CI unless tokens are passed explicitly. — [claudeissues.com docs issue](https://claudeissues.com/issue/69620-docs-headless-and-agent-sdk-mcp-docs-do-not-explain-unauthenticated-server-behav)
- Hooks for guarding tools: a `PreToolUse` hook can emit `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"..."}}` (or exit 2) to block a call; matchers for MCP tools need a regex such as `mcp__memory__.*` or `mcp__.*__write.*`; the `if` field accepts permission-rule syntax like `"Bash(rm *)"`; `updatedInput` can rewrite arguments before execution; `onFailure: "block"` (v2.1.295+) makes a timed-out hook block. — [Claude Code hooks docs](https://code.claude.com/docs/en/hooks)
- Mobile device MCP: `mobile-mcp` tools include `mobile_list_available_devices` and work on simulators, emulators and real devices. — [mobile-mcp GitHub](https://github.com/mobile-next/mobile-mcp)
- Revyl (YC F24, mobile) ships a CLI with agent "skills"; a hosted agent with `REVYL_API_KEY` is pre-authenticated and runs `revyl auth persist-cloud-env` so an MCP server that does not inherit the variable can use it; `revyl dev --remote --detach --json` starts a cloud device and returns a `viewer_url`; MCP/editor setup is documented at docs.revyl.com/cli/mcp-setup. — [revyl-cli README](https://raw.githubusercontent.com/RevylAI/revyl-cli/main/README.md)
- Revyl skills catalog (third-party listing): one skill "verifies a mobile PR by matching the exact commit SHA to a CI-uploaded Revyl build, then collects device evidence and prepares a proof summary without rebuilding"; another "starts a device from a build ID, captures evidence, and comments on the PR". — [SkillsMP listing](https://skillsmp.com/creators/revylai/revyl-cli); [Cursor marketplace](https://cursor.com/marketplace/revyl)
- Monday.com runs an AI agent in CI that collects failed Playwright job logs and stack traces, inspects the PR diff and posts contextual feedback back to the PR. — [monday.com engineering](https://engineering.monday.com/?p=11772)

### Inferences
- Recommended wiring for a PR verifier in GitHub Actions (inference from the docs above): (1) `on: pull_request` with `permissions: contents: read, pull-requests: read, issues: read, checks: write` (checks only if you publish a check run); (2) `claude_args` with `--mcp-config /tmp/device.json --allowedTools "mcp__github__get_pull_request,mcp__github__get_pull_request_diff,mcp__github__get_issue,mcp__device__*" --disallowedTools "Bash,Edit,Write" --max-turns 60`; (3) a `PreToolUse` hook that denies `mcp__device__.*` calls whose arguments contain destructive intents (delete/pay/send) or target hosts outside the test device/allow-list; (4) run the device MCP server as a separate process holding the device credentials so Claude never sees them.
- Give the agent two disjoint servers rather than one: a read-only GitHub server (or `gh` restricted to `Bash(gh pr view:*)`, `Bash(gh pr diff:*)`) and a device server whose own backend enforces read-only / sandbox semantics (the DBHub `readonly = true` precedent): defense in depth means the tool server, not the prompt, is the enforcement point.
- For fork PRs, do not rely on secrets being available; use `pull_request_target`/`workflow_run` only with the base-ref-at-root + `--add-dir pr-head` pattern (see KQ5) and treat PR text as untrusted input.

- No official Anthropic example combining a computer-use/device MCP server with the GitHub action in one workflow; the pattern is assembled from separate docs.
- Could not fetch Revyl's docs or skill files (GitHub API access to the repo not enabled in this session), so the exact schema of its "proof summary" is unverified.
- Codex CLI and Cursor MCP-for-devices usage was not researched in depth (no primary sources found in searches); only mobile-mcp's claim of compatibility with Codex/Copilot/Gemini.

## KQ3. Test-plan generation: diff → affected features → scenarios; acceptance criteria from tickets

### Takeaway
The research pattern that maps best to PR verification is "change-directed differential testing": use an LLM to do change-impact analysis from the diff plus the stated intent, generate scenarios that exercise the changed behaviour, run them on pre-change and post-change builds, and classify each observed difference as intended or unintended (Testora, DiffTestGen, RippleGUItester — the latter found 26 previously unknown bugs in Firefox/Zettlr/JabRef/Godot). Acceptance-criteria generation from user stories into Gherkin is reported as ~95% "helpful" in an industrial study but there is no correctness benchmark; practitioners anchor the diff to routes/selectors/test-ids and fall back to the full suite when shared components change.

### Cited Findings
- RippleGUItester (Su, Pradel, Chen; arXiv 2603.03121, submitted 2026-03-03): "change-driven testing" that starts from a code change, runs LLM-based change-impact analysis to generate and enrich GUI test scenarios, executes them on pre-change and post-change versions, applies differential analysis, and uses a multimodal step comparing visual GUI changes against natural-language change intents to separate unintended bugs from intended updates; evaluated on hundreds of real changes in Firefox, Zettlr, JabRef and Godot; 26 previously unknown bugs, 16 fixed, 2 confirmed, 6 under discussion, 2 marked intended. — [arXiv 2603.03121](https://arxiv.org/abs/2603.03121)
- Testora (Pradel, arXiv 2503.18597): LLM generates tests exercising the modified code, runs them on original and modified versions, and classifies each behavioral difference as intended or unintended to catch regressions. — [arXiv 2503.18597 (snippet)](https://www.arxiv.org/pdf/2503.18597)
- DiffTestGen (arXiv 2607.16024): takes a GitHub PR and codebase, builds a prompt, runs an error-fixing loop, tracks coverage of the changed lines and feeds it back into further generation rounds. — [arXiv 2607.16024 (snippet)](https://arxiv.org/pdf/2607.16024)
- PR-Aware Automated Unit Test Generation (arXiv 2605.25285, May 2026): scores success as fail-to-pass tests (fail before the change, pass after); both EvoSuite and GPT-4o mostly fail — about 64% of PRs got no meaningful change-capturing test; results broken down by PR size; Java dataset released. — [arXiv 2605.25285 (snippet)](https://arxiv.org/pdf/2605.25285)
- Meta's "catching tests" work (arXiv 2601.22832) uses LLMs to infer developer intent and generate targeted tests on diffs (overview only). — [alphaXiv overview](https://www.alphaxiv.org/overview/2601.22832)
- "Can LLM Generate Regression Tests for Software Commits?" (arXiv 2501.11086) critically examines whether LLMs can produce regression tests exposing bugs introduced or fixed by a commit/PR. — [arXiv 2501.11086](https://arxiv.org/html/2501.11086v1)
- AutoUAT / Test Flow industrial case study (arXiv 2504.07244, GPT-4 Turbo, automotive partner): Gherkin acceptance scenarios generated from user-story titles and descriptions were judged helpful 95% of the time "even revealing previously overlooked cases"; generated Cypress scripts 92% helpful; "helpful" is a self-reported judgment, not correctness/coverage. — [arXiv 2504.07244](https://arxiv.org/html/2504.07244v1)
- Practitioner pattern for E2E impact analysis: extract from the diff what changed (selectors, routes, IDs, visible text) and match against test files; coverage-based selection "breaks down for E2E (where the 'coverage' is a running browser)". — [DEV Community](https://dev.to/gabrielholmesqa/how-to-know-which-tests-a-pr-will-break-before-ci-runs-44b8)
- A Claude skill "e2e-pr" maps changed files to affected pages and runs targeted specs, falls back to the full suite when shared components or layouts change, and flags changed routes that lack coverage. — [skills.rest e2e-pr](https://skills.rest/skill/e2e-pr)
- Augment's spec-to-Gherkin workflow reads updated Jira/Linear acceptance criteria, writes one Gherkin scenario per criterion, generates executable tests, and includes a human clarification step for ambiguous criteria (how-to, no accuracy data). — [Augment Code workflow](https://www.augmentcode.com/workflows/qa/spec-to-gherkin-tests)
- Anthropic Code Review's `REVIEW.md` supports a "verification bar" such as "behavior claims need a `file:line` citation in the source, not an inference from naming", which Anthropic says "cuts false positives". — [Claude Code Review docs](https://code.claude.com/docs/en/code-review)

### Inferences
- Concrete pipeline (synthesised from RippleGUItester/Testora + practitioner anchors):
  1. **Intent extraction**: from PR title/body + linked ticket, produce `change_intent` (1–3 sentences) and `claimed_behaviors[]` (each: `id`, `text`, `source: pr_body|ticket|commit`, `kind: new|changed|removed|fixed`).
  2. **Impact mapping**: static pass over the diff to collect `anchors` = {routes/screens (router files, navigation graphs, Expo/Flutter route tables), component names, test-ids/accessibility labels, feature flags, i18n keys, API endpoints}; join with a repo "screen map" (routes → screens → entry flows) built once and cached; mark `blast_radius: local|shared_component|layout|global`.
  3. **Scenario generation** (LLM): for each claimed behavior produce Given/When/Then scenarios with `preconditions` (account state, feature flags, seed data), `steps[]` (natural-language, device-agnostic), `oracles[]` (see KQ4), `negative_control` (a step that must NOT change / an input that must be rejected), and `expected_on_base: same|different` — the last field enables pairwise base-vs-PR comparison.
  4. **Coverage check**: every `claimed_behavior` must map to ≥1 scenario; changed routes with no scenario are reported as `unverified_change` (the e2e-pr skill pattern); if `blast_radius ∈ {shared_component, layout, global}` add smoke scenarios for the top-N screens.
- Suggested test-plan prompt skeleton (inference): system = role + hard rules ("only claim behaviours stated in PR/ticket or visible in diff; cite the diff hunk or ticket line for each; prefer scenarios observable on screen; output JSON matching schema"); user = {ticket, PR body, diff hunks grouped by file, screen map excerpt, feature-flag defaults}; ask for `scenarios[]` and a `cannot_verify_via_ui[]` list with reasons (backend-only, needs prod data, requires payment).
- Given the 64%-of-PRs-without-a-capturing-test result for unit tests, expect the UI-level plan to also miss or over-generate; treat the plan as a draft the report must expose (so reviewers see what was and wasn't checked).

### Gaps
- No benchmark comparing precision/recall of static anchor matching vs LLM impact analysis for E2E selection.
- No correctness benchmark for ticket→Gherkin generation (only "helpfulness" ratings).
- RippleGUItester prompts and schemas not readable here (arXiv blocked); only abstract-level description.

## KQ4. Verification oracles: LLM-as-judge on screenshots, voting, rubrics, pairwise before/after, pixel diffs, a11y assertions; reducing hallucinated "pass"

### Takeaway
LLM/VLM judges of GUI trajectories have a documented false-positive problem: even the best web-agent judges reach only ~70% precision (AgentRewardBench), judges are fooled by "surface UI match" and partial completion (Mobile-JudgeBench), and rewriting an agent's chain-of-thought alone raised VLM-judge false-positive rates by up to 90% (Gaming the Judge). Mitigations with evidence: judge from observations not from agent narration, require specific evidence snapshots, unanimous multi-query voting, and combine with deterministic oracles (a11y-tree assertions, pixel/perceptual diffs with anti-aliasing suppression, before/after on base vs PR).

### Cited Findings
- AgentRewardBench (arXiv 2504.08942, web agents): even the best LLM judges reached only about 70% precision on success detection, i.e. roughly 30% of "success" labels were wrong; precision was prioritised because false positives most damage rejection fine-tuning and reward modelling. — [AgentRewardBench](https://arxiv.org/html/2504.08942v2)
- Mobile-JudgeBench (arXiv 2608.11434, Aug 2026): 931 human-annotated mobile trajectories; failure taxonomy includes "surface UI match" (judge fooled by a screen resembling the target) and "partial completion" (unmet subtasks overlooked); a simple baseline using sampled screenshots is competitive with elaborate judge pipelines; the LLM backbone matters most, with one backbone conservative and another permissive. — [Mobile-JudgeBench](https://arxiv.org/pdf/2608.11434)
- Gaming the Judge (arXiv 2601.14691): rewriting agent chain-of-thought while keeping actions/observations fixed raised VLM-judge false-positive rates by up to 90%; content manipulations fabricating signs of progress were most effective; prompting techniques and extra judge-time compute reduced but did not eliminate the problem. — [Gaming the Judge](https://arxiv.org/html/2601.14691v2)
- WindowsWorld (arXiv 2604.27776): false positives occur "when an action looks successful in the trajectory history, but window changes hide the actual GUI state". — [WindowsWorld (snippet)](https://arxiv.org/pdf/2604.27776)
- GUI-agents-with-RL survey (arXiv 2604.27955): ZeroGUI uses multi-query unanimous voting over trajectory screenshots to reduce false positives; SmartSnap has the agent capture visual evidence so judges can check specific snapshots. — [survey (snippet)](https://arxiv.org/pdf/2604.27955)
- TRAP benchmark authors argue earlier injection benchmarks "rely on LLM judges that can misclassify whether an agent refused or simply failed". — [TRAP, arXiv 2512.23128](https://arxiv.org/abs/2512.23128)
- Anthropic Code Review (managed service, research preview, launched 2026-03-09): "multiple agents analyze the diff... then a verification step checks candidates against actual code behavior to filter out false positives"; findings carry a collapsed "Why this was flagged" section explaining "how it verified the problem"; secondary coverage reports <1% of findings marked incorrect by engineers (a dismissal rate, not ground truth) and an 80% confidence posting threshold (single source, unconfirmed). — [Claude Code Review docs](https://code.claude.com/docs/en/code-review); [vktr.com](https://www.vktr.com/ai-news/anthropic-launches-multi-agent-code-review-for-claude-code/); [interviewkickstart (threshold claim)](https://interviewkickstart.com/blogs/articles/claude-code-now-uses-ai-agents-to-review-pull-requests-what-engineers-need-to-know)
- Pixel diffing: pixelmatch `threshold` is 0–1 (default 0.1, smaller = more sensitive) and `includeAA` (default false) excludes anti-aliased pixels from the count; SSIM gives one global score (common cutoff ~0.95 in one project) but does not isolate changed regions; anti-aliased edges across DPI/font-hinting differences are "a leading cause of false failures". — [pixelmatch on socket.dev](https://socket.dev/npm/package/pixelmatch/overview/^4.0.0); [@blazediff/matcher](https://jsr.io/@blazediff/matcher@2.0.7); [autocontrol YIQ diff notes](https://autocontrol.readthedocs.io/en/latest/Eng/doc/new_features/v149_features_doc.html)
- odiff: native (Zig, SIMD) pixel-by-pixel diff in milliseconds, cross-format (png/jpg/webp/tiff), anti-aliasing detection, ignore regions, YIQ perceptual difference, different-layout support, Node binding `compare(img1, img2, diffPath)` returning `{match, reason}`, and a server mode to avoid process spawn overhead. — [odiff README](https://raw.githubusercontent.com/dmtrKovalenko/odiff/main/README.md)
- tester-army/e2e mixes agent steps with deterministic checks in one test: `agent.act(...)`, `agent.assert('the invoice preview shows a prorated amount')` and Playwright-style `expect(screen.getByRole('status')).toContainText('Pro')`; "agent.assert, agent.waitFor, and agent.extract always run live, so checks never come from a recording". — [tester-army/e2e README](https://raw.githubusercontent.com/tester-army/e2e/main/README.md); [everydev summary](https://www.everydev.ai/tools/e2e)
- Octomind separates real bugs from UI changes by analysing the Playwright Trace and DOM snapshot and compares against the last successful run. — [Octomind self-healing page](https://octomind.dev/product/playwright-self-healing/); [Octomind debug page](https://octomind.dev/product/debug-tests)
- RippleGUItester's multimodal step compares GUI changes against natural-language change intents to separate unintended bugs from intended updates (pairwise pre/post differential). — [arXiv 2603.03121](https://arxiv.org/abs/2603.03121)

### Inferences
- Oracle hierarchy (strongest first), to be encoded per scenario: (1) deterministic a11y/DOM assertion (`getByRole/Text/TestId` exists / has text / is enabled); (2) deterministic state oracle (network call observed, API/DB read via read-only tool); (3) pairwise differential: same flow on base build and PR build, deterministic diff of a11y trees + odiff/pixelmatch with `includeAA=false`/ignore-regions for dynamic areas, then an LLM only labels the diff as intended vs unintended relative to `change_intent`; (4) rubric-based VLM judgment on screenshots with a fixed rubric and required evidence citation; (5) free-form judgment — allowed only to downgrade to "unable to verify", never to produce a PASS.
- Judge prompt rules that follow from the evidence: feed the judge observations (screenshots/a11y snapshots) and the original expected outcome, NOT the executor agent's narration or chain-of-thought (Gaming the Judge); require the judge to name the screenshot index and region/element that proves each criterion (SmartSnap pattern; Anthropic's `file:line` citation rule analogue); force a check-list over every sub-criterion to counter "partial completion"; include a negative control (e.g. "the old label must NOT be present", "base build must NOT show the new element") so a judge that says "pass" to everything is caught; run N=3 independent judge samples (ideally two different model families) and treat PASS only if unanimous (ZeroGUI), otherwise `inconclusive`.
- Output schema per criterion (inference): `{criterion_id, verdict: pass|fail|inconclusive|unable_to_verify, evidence:[{screenshot_id, bbox|element_ref, note}], negative_control: {checked: bool, result}, judge_votes: [..], confidence: 0-1, oracle_type}`. Confidence should be derived from oracle type + vote agreement, not asked from the model as a bare number.
- Pixel diffs are a good *detector* of change but a poor *verdict*; use them to (a) find screens that changed between base and PR to focus the plan, and (b) catch unintended visual regressions on screens the PR should not have touched.

### Gaps
- Exact accuracy/F1 tables of Mobile-JudgeBench and the mitigation numbers in Gaming the Judge could not be read (arXiv/alphaXiv blocked); only snippet-level claims.
- No study found that quantifies the benefit of negative controls or evidence-citation requirements specifically for UI judges; these are inferred from the code-review analogue and from SmartSnap/ZeroGUI.
- No head-to-head reliability data for "a11y-tree assertions + vision" vs vision-only judges.

## KQ5. Determinism, caching and replay: record once, replay deterministically, fall back to the agent on drift; invalidation when the PR changes UI

### Takeaway
Every serious AI-testing product has converged on the same architecture: the agent authors or records a deterministic script (Playwright/Appium code or an action trace), replay is deterministic and model-free, and the agent is invoked only when the replay breaks (locator healing within the run; permanent healing via a PR). Cache keys combine the step instruction, page/screen content and options; replays are invalidated when the app's observable state no longer matches, and assertions are always executed live.

### Cited Findings
- tester-army/e2e: "An agent step that a later assertion verifies records its actions, and the next run replays them with no model calls until the app changes. Tests without agent steps need no model."; CI mode switches this on automatically "with one retry and a read-only trace cache"; each cached step is reported as replayed, handed off, or missed; `npx e2e run --no-cache` bypasses the cache; mobile engine uses simulators/emulators through agent-device; `@e2e-dev/github` posts results as a PR comment. — [tester-army/e2e README](https://raw.githubusercontent.com/tester-army/e2e/main/README.md); [everydev summary](https://www.everydev.ai/tools/e2e)
- Momentic layered healing: locator healing re-resolves a stale target from the step's description within the run without editing the test; "transient recovery" (beta) proposes and executes step changes, runs only once per test run and only if the test passed in the last 7 days, and will not attempt a second recovery if a later step also fails "to avoid compounding errors"; a post-run triage agent can permanently rewrite failing tests and open a PR or emit a patch; quarantine removes unresolved flaky tests from blocking CI; successful paths stay fast through deterministic replay and step caching, and an eligible successful run can be saved to the step cache. — [Momentic auto-heal docs](https://momentic.ai/docs/reliability/auto-heal.md); [Momentic auto-maintenance](https://momentic.ai/docs/reliability/auto-maintenance); [Momentic failure recovery](https://momentic.ai/docs/platform/auto-healing/failure-recovery)
- Stagehand: caching is keyed on the instruction, page content and call options; cache hits skip the LLM; server-side caching requires a Browserbase browser; `selfHeal` re-infers the action and retries once when a recorded selector stops resolving; vendor-reported savings range from ~30% to "up to 90%" for repeated workflows; `act()` ~500–2,000 tokens per call. — [Stagehand act docs](https://docs.stagehand.dev/v4/basics/act); [Stagehand cost optimization](https://docs.stagehand.dev/v3/best-practices/cost-optimization); [Mintlify mirror](https://www.mintlify.com/browserbase/stagehand/best-practices/cost-optimization)
- Octomind stores each test as an interaction chain and "generate[s] the corresponding Playwright code deterministically on the fly immediately prior to test execution"; failure analysis uses the Playwright trace and DOM snapshot; broken selectors get a proposed code fix; timing flakiness is handled by internal stabilisation (auto-retries, dynamic waits). — [Octomind under the hood](https://octomind.dev/docs/more-info/under-the-hood); [Octomind self-healing](https://octomind.dev/product/playwright-self-healing/)
- QA Wolf: AI generates deterministic Appium and Playwright code; marketing contrasts this with agents relying on screen-driven computer use "which it describes as expensive to run". — [QA Wolf Automation AI](https://www.qawolf.com/automation-ai)
- Other deterministic-replay tooling: Docker cagent records an agent session and replays it VCR-style, matching incoming requests against the recording; flowproof "agents author, a deterministic engine executes" (record once, replay with no LLM calls); agrepl is an academic CLI for deterministic replay of agent executions. — [Docker cagent blog](https://www.docker.com/blog/deterministic-ai-testing-with-session-recording-in-cagent/); [flowproof on PyPI](https://pypi.org/project/flowproof/0.8.0/); [arXiv 2607.16200](https://arxiv.org/abs/2607.16200)
- Callstack agent-device has an experimental "Replay & E2E Testing" mode with the same record-then-replay idea for mobile. — [agent-device docs](https://oss.callstack.com/agent-device/docs/replay-e2e)
- Note: the GitHub project `magnitudedev/magnitude` is now a local inference engine (kernel tuning, "2x faster than Ollama"), not an AI web-testing framework; older write-ups describing Magnitude as an open-source AI web-testing tool with a planner/executor split refer to the earlier product. — [magnitude README](https://raw.githubusercontent.com/magnitudedev/magnitude/main/README.md); [HF blog (older)](https://huggingface.co/blog/lynn-mikami/magnitude-open-source-ai-agents-web-testing)

### Inferences
- Cache design for a PR verifier: key = hash(scenario_id, step_index, step_instruction, normalized a11y-tree fingerprint of the screen before the step, device profile/OS version, app build "UI signature"). Store the resolved action (element ref + fallback coordinates + a11y path). On replay: if the fingerprint matches → execute deterministically; if the target element is missing but the fingerprint is close → locator-heal (one LLM call) and continue; if the screen fingerprint differs materially → "drift", hand the step to the agent and mark the step as `handed_off` in the report (tester-army vocabulary).
- Invalidation on PR change: compute a per-screen "UI signature" from the PR impact map (KQ3) — any screen whose components/routes/strings/flags appear in the diff gets its cached steps marked `stale` so they run agent-first on this PR; unaffected screens replay from cache. Also invalidate when the a11y fingerprint distance exceeds a threshold at runtime, and never cache assertions (always live), per tester-army and Momentic.
- Flakiness policy modelled on Momentic: at most one AI recovery per scenario run; no recovery if a later step fails after a recovery; two runs required before labelling a failure as a product regression; quarantine instead of blocking.

### Gaps
- None of the sources specify exactly how "the app changes" is detected for cache invalidation (tester-army) — likely DOM/a11y fingerprinting, but not confirmed.
- Momentic and Stagehand pages could not be read directly (blocked); details come from search snippets of their docs.
- No independent measurement of replay hit rates or cost savings; all cost-saving figures are vendor-reported.

## KQ6. Security: prompt injection from app content, confining the agent to the test device, secrets, cost caps, fork PRs

### Takeaway
Prompt injection through screen content is real and measured: Anthropic's Claude-for-Chrome red-team showed 23.6% attack success without mitigations → 11.2% with (autonomous mode), and TRAP (ICML 2026) found frontier models diverted in ~25% of tasks on cloned sites; Anthropic's API now runs classifiers over tool-returned content including screenshots. The engineering controls are environmental (dedicated VM/device, allow-listed domains, no credentials in reach, read-only tool servers, hooks that deny destructive calls, `--max-turns`/`--max-budget-usd`/timeouts) plus GitHub-side rules (write-access actor check, base-ref checkout for `pull_request_target`, secrets withheld on fork PRs).

### Cited Findings
- Anthropic computer-use docs: use a dedicated VM or container with minimal privileges, withhold sensitive data and credentials, allow-list domains, require human confirmation for consequential actions (payments, consent, ToS); "Anthropic's classifiers scan tool-returned content, including screenshots, for prompt injection. When they flag something, Claude checks whether the instruction really came from the user"; inform end users and get consent. — [Anthropic computer use tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)
- Claude for Chrome red-team (Aug 2025): 123 cases across 29 attack scenarios; attack success 23.6% without mitigations in autonomous mode, reduced to 11.2% with safeguards (vs 19.4% for the older Computer Use capability); on four browser-specific attack types (hidden form fields, URL/title injections) success fell from 35.7% to 0%; one mitigated attack had Claude delete a user's emails on instructions embedded in an incoming message; safeguards are site-level permissions, confirmation before high-risk actions, and category blocks (financial, adult, pirated content). Simon Willison called 11.2% "still a catastrophic failure rate". — [Anthropic news](https://www.anthropic.com/news/claude-for-chrome); [Simon Willison](https://simonwillison.net/2025/Aug/26/piloting-claude-for-chrome/); [The Register](https://www.theregister.com/2025/08/26/anthropic_claude_chrome_warnings/)
- TRAP (Task-Redirecting Agent Persuasion Benchmark, arXiv 2512.23128, ICML 2026): persuasion-based injections across clones of Amazon, Gmail, Google Calendar, LinkedIn, DoorDash, Upwork; six frontier models were diverted in about a quarter of tasks (GPT-5 13% low end, DeepSeek-R1 43% high end); small interface/context changes often roughly doubled success rates; cites real incidents (Perplexity Comet malicious directive, hidden white text in Gmail manipulating Gemini). — [TRAP](https://arxiv.org/abs/2512.23128); [ICML 2026 listing](https://icml.cc/virtual/2026/78577)
- WASP (Meta, arXiv 2504.18575) evaluates end-to-end whether web agents resist injections in a VisualWebArena sandbox; WAInjectBench (arXiv 2510.01354) finds detectors catch explicit textual/visible attacks with moderate-high accuracy but largely miss attacks without explicit instructions or with imperceptible perturbations. — [WASP](https://arxiv.org/pdf/2504.18575v1.pdf); [WAInjectBench](https://www.alphaxiv.org/abs/2510.01354.md)
- claude-code-action security: only users with write access can trigger (checked for issue/PR/comment/review and for `workflow_run` both actors); bots blocked unless in `allowed_bots` (explicit list preferred over `'*'`; allowed bots are not permission-checked); `allowed_non_write_users` is "RISKY", works only with a provided `github_token`, enables best-effort scrubbing of Anthropic/cloud/GitHub secrets from subprocess environments and bubblewrap PID-namespace isolation on Linux, and `CLAUDE_CODE_SCRIPT_CAPS` can cap calls per helper script; never use a PAT with it because "a static token ... could be partially or fully recovered over time via prompt injection". — [claude-code-action security.md](https://raw.githubusercontent.com/anthropics/claude-code-action/main/docs/security.md)
- Fork PRs: `pull_request_target` and `workflow_run` run with the base repository's secrets; "Do not check out an untrusted ref into the workspace root before this action" — check out the base ref at root and the PR head into a subdirectory passed via `--add-dir pr-head`; the action restores `.claude/`, `.mcp.json`, `.claude.json`, `.gitmodules`, `.ripgreprc`, `CLAUDE.md`, `CLAUDE.local.md`, `.husky/` from the base branch (PR versions kept under `.claude-pr/` for reference), but `package.json`, lockfiles, `Makefile`, `node_modules/`, linter configs and `bunfig.toml`/`.npmrc` stay PR-controlled, so hooks must invoke pinned tools directly rather than `npm run ...`. — [claude-code-action security.md](https://raw.githubusercontent.com/anthropics/claude-code-action/main/docs/security.md)
- The action sanitises untrusted content by stripping HTML comments, invisible characters, markdown image alt text and hidden HTML attributes, and warns about hidden markdown when tagging Claude on untrusted content; `show_full_output` is off by default because logs are public on public repos and may contain tokens; GitHub Actions debug mode auto-enables it. — [claude-code-action security.md](https://raw.githubusercontent.com/anthropics/claude-code-action/main/docs/security.md)
- Managed Code Review never reviews a fork PR automatically; only a `@claude review` comment from someone with write access to the base repo triggers it. — [Claude Code Review docs](https://code.claude.com/docs/en/code-review)
- Cost caps: Claude Code 2.1.283 has `--max-budget-usd <amount>` for `-p` runs (per-invocation, not team-wide); pair with `--max-turns`; on subscription OAuth the estimated token cost is compared against the limit so a run may stop even though the subscription covers it. — [youcanbuildthings](https://youcanbuildthings.substack.com/p/how-to-cap-a-claude-code-loops-spend); [backgroundclaude headless](https://backgroundclaude.com/headless); [aident.ai](https://aident.ai/blog/fix-claude-code-max-budget-usd-subscription)
- Anthropic's own cost levers for the action: `--max-turns`, workflow timeouts, concurrency controls; Code Review offers an org-level monthly spend cap and skips reviews (posting one comment) when the cap or usage credits are exhausted. — [Claude Code GitHub Actions docs](https://code.claude.com/docs/en/github-actions); [Claude Code Review docs](https://code.claude.com/docs/en/code-review)
- Agent SDK permission guidance: prefer `allowedTools` wildcards per server over `bypassPermissions`; the DBHub example enforces read-only in the tool server (`readonly = true`). — [Agent SDK MCP docs](https://code.claude.com/docs/en/agent-sdk/mcp)
- Hooks: `PreToolUse` can deny or rewrite (`updatedInput`) tool calls, matchers `mcp__.*__write.*`; `if` filter is best-effort so "use the permission system for hard allow/deny rules". — [Claude Code hooks docs](https://code.claude.com/docs/en/hooks)
- Revyl documents sandboxed/headless runner setup covering a writable home, non-interactive PATH, proxy and CA trust, minimum egress, and "the boundary between local inspection and authorized cloud actions". — [revyl-cli README](https://raw.githubusercontent.com/RevylAI/revyl-cli/main/README.md)

### Inferences
- Threat model for a PR verifier has three injection surfaces: PR/ticket text (sanitise + treat as data; never let it define allowed tools), app screen content (test seed data and third-party content can carry instructions — keep the device isolated, no real accounts, network egress allow-listed to the app backend/staging), and the diff itself (code comments can address the agent). The report should record if the agent received any instruction-like text from the screen and ignored it.
- Hard controls > prompt controls: (a) device MCP server exposes only tap/type/swipe/screenshot/a11y-snapshot on a named test device ID and refuses other devices; (b) `--disallowedTools Bash,Edit,Write` for the verifier role; (c) `PreToolUse` deny for `mcp__device__.*` when `text` input matches secret patterns or when the current foreground app is not the app under test; (d) `--max-turns`, `--max-budget-usd`, `timeout-minutes`, `concurrency: group: verify-${{ github.event.pull_request.number }}` with `cancel-in-progress: true`; (e) per-PR budget stored as a check-run output so repeated pushes cannot multiply spend without a human re-request (mirror of Code Review's manual mode for forks).
- For fork PRs: run the verifier only on `@verify` comment from a write-access user, build the app from the fork head in an isolated job without secrets, and run the agent job on the base ref with the artifact (built app) as input — this keeps secrets away from fork-controlled code while still testing the fork's build.

### Gaps
- No 2026 update from Anthropic on Claude-for-Chrome / computer-use injection success rates after Aug 2025.
- No published measurements of injection via mobile app screens (all benchmarks are web/browser).
- `--max-budget-usd` exact exit behaviour and interaction with the GitHub action are documented only by third parties.

## KQ7. Evidence / report design: what makes a verification report trustworthy

### Takeaway
Trustworthy reports in shipping tools share five traits: every finding is anchored to a precise location/artifact (inline comment on a diff line, step screenshot, Playwright trace/DOM snapshot, video), the reasoning and the verification method are exposed but collapsed ("Why this was flagged"), severity/confidence is explicit and never silently blocks the merge (neutral check run with machine-readable counts), negative/absent results are stated ("no issues detected", "unable to verify"), and reviewers can rate the finding so the system is tuned on dismissals.

### Cited Findings
- Anthropic Code Review posts findings as inline comments on the exact lines, tagged 🔴 Important / 🟡 Nit / 🟣 Pre-existing, each with a collapsed "Why this was flagged" section explaining how it verified the problem; a summary in the review body; a "Claude Code Review" check run with a severity table (`Severity | File:Line | Issue`) and diff annotations written independently of inline comments "so they remain available even if GitHub rejects an inline comment on a line that moved"; the check run "always completes with a neutral conclusion so it never blocks merging"; the Details text ends with a machine-readable comment parsable with `gh api ... --jq '.output.text | split("bughunter-severity: ")[1] | split(" -->")[0] | fromjson'` returning e.g. `{"normal": 2, "nit": 1, "pre_existing": 0}`; findings come with 👍/👎 reactions used to tune the reviewer; "If no issues are found, Code Review updates the GitHub check run to show that no issues were detected"; reviews average ~20 minutes and $15–25. — [Claude Code Review docs](https://code.claude.com/docs/en/code-review)
- `REVIEW.md` levers that shape report trust: a "verification bar" (evidence citation required before posting a class of finding), nit caps ("report at most five nits, mention the rest as a count"), re-review convergence rules, and a "summary shape" opening with a one-line tally such as `2 factual, 4 style` or "no factual issues". — [Claude Code Review docs](https://code.claude.com/docs/en/code-review)

### Inferences
- Report structure recommended for a PR verifier (synthesised from the above):
  1. **Header tally** (one line): `3 criteria verified, 1 failed, 1 unable to verify · build <sha7> on <device/OS> · base vs PR compared on 4 screens · cost $X · 7 min`.
  2. **Criteria table**: `criterion (from ticket/PR, with source link) | verdict | oracle type | evidence links (step #, screenshot, a11y snapshot, trace) | confidence (derived) | notes`.
  3. **Per-step strip**: numbered screenshots with annotated click/tap points and the a11y element targeted; mark each step `replayed | healed | agent | handed_off`; include base-branch twin screenshot where a pairwise comparison was made, with the odiff heatmap.
  4. **Negative controls and non-findings**: explicitly list "checked and unchanged" screens and the negative controls that held.
  5. **Unable-to-verify section** with reason codes: `backend_only`, `needs_prod_data`, `blocked_by_guardrail` (e.g. payment), `budget_exhausted`, `device_unavailable`, `drift_unresolved`; this is the honest counterpart to Code Review's "no issues detected".
  6. **Collapsed "how this was verified"** per criterion (judge votes, oracle used, what would have falsified it) — mirroring "Why this was flagged".
  7. **Machine-readable footer** (HTML comment JSON) with counts per verdict so CI can gate if the team chooses, while the check run itself stays neutral.
  8. **Feedback affordance**: 👍/👎 on each finding and a `@verify again` command.
- Trust is increased by linking evidence to immutable artefacts (commit SHA, build ID, device/OS, scenario version, cache hit/miss) so a reviewer can distinguish "the agent saw it" from "the agent inferred it" — the Revyl SHA-to-build match and Code Review's independence of annotations from inline comments are the concrete precedents.
