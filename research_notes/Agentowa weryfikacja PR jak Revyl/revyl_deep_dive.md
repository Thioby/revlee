## Key Question 1 — Exact developer workflow from "open PR" to "verdict", and which GitHub integrations exist

### Takeaway
Revyl has three distinct PR-verification paths: (A) the hosted **Revyl GitHub App** with **"Proof of Changes"** (config-as-code in `.revyl/config.yaml`; the Revyl agent checks the PR out in a disposable sandbox, builds or receives a build, installs it on a cloud simulator/emulator, exercises the diff, and renders a graded verdict into a single Revyl comment block on the PR); (B) a **BYO-CI + coding-agent** path (GitHub Actions uploads a build with `revyl build upload`, then Claude Code / Cursor drives `revyl device …` commands and posts a comment itself); (C) **CLI-driven regression** (`revyl workflow run` / `revyl test run` from the official GitHub Actions `run-test`, `run-workflow`, `upload-build`). The GitHub App path became generally available on 2026-09-04 and graded verdicts shipped 2026-09-18.

### Cited Findings

**Path A — Revyl GitHub App + Proof of Changes (hosted agent)**
- "Every time someone opens a pull request (PR), Revyl can install that PR's build on a live device, run through the changed flows, and post a verdict." — [docs: Proof of Changes](https://docs.revyl.com/develop/proof-of-changes)
- Default prover: "the Revyl agent … checks the PR out in an isolated sandbox, drives cloud devices against the preview build, and posts its write-up on the same Revyl block as preview builds. The checkout is disposable and never holds a credential that can write to your repository." — [docs: GitHub](https://docs.revyl.com/integrations/github); [docs: Proof of Changes](https://docs.revyl.com/develop/proof-of-changes)
- Setup: install the GitHub App from Settings → Integrations → GitHub in the dashboard (or `revyl github connect`, which "only installs or verifies access, and it never changes or publishes `.revyl/config.yaml`"); then `revyl github setup` writes the `pr_review` policy into `.revyl/config.yaml` and validates it. — [docs: GitHub](https://docs.revyl.com/integrations/github)
- Config lives at the project root: `.revyl/config.yaml` (repo root) or e.g. `apps/consumer/.revyl/config.yaml` for a nested project; "The config path defines the project root." — [docs: GitHub](https://docs.revyl.com/integrations/github)
- Since 2026-09-04 "pull requests use the Revyl config from their own commit, so a config change gets checked in the same pull request", and "GitHub repository automation is now available to all workspaces, no longer limited to early access. Each app also gets a single preview link that always opens its latest build." — [changelog 2026-09-04](https://revyl.com/changelog/2026-09-04/)
- Triggers: `review_triggers.paths` (globs), `review_triggers.labels` (`!` prefix excludes), `review_triggers.drafts` (when true, drafts are eligible). "If review_triggers.paths is empty, a nested project defaults to its own root folder and its subfolders." — [docs: GitHub](https://docs.revyl.com/integrations/github)
- Builds: `pr_review.build.kind` is either `revyl` (Revyl-managed cloud build from a named `build.profiles.<name>` recipe, e.g. `profile: pull-request`) or `ci_upload_to_revyl` (your CI uploads the artifact; `app_ids.ios` / `app_ids.android` map to Revyl apps). (source code: `internal/config/contracts.go` `AuthoredReviewBuild{Kind, Profile, AppIDs}`; `compiler.go` line ~808) — [contracts.go](https://github.com/RevylAI/revyl-cli/blob/main/internal/config/contracts.go)
- Proof policy keys (canonical, validated by the CLI): `pr_review.proof_of_changes.enabled`, `.harness.kind` (`revyl` default | `cursor`), `.harness.model_id` (Cursor-only, 1–255 chars), `.system_prompt` (extra guidance prepended to proof runs), `.always_verify` (list of natural-language invariants). Also `pr_review.workflow_ids` (saved Revyl workflows to run against the preview build) and `pr_review.strict_ci_check.build` (bool: "when true, a failed managed build produces a failing build check"). (source code: `internal/config/compiler.go` lines 390–480; `contracts.go` lines 90–140) — [compiler.go](https://github.com/RevylAI/revyl-cli/blob/main/internal/config/compiler.go), [docs: GitHub](https://docs.revyl.com/integrations/github)
- **[older]** legacy schema (still parsed and auto-migrated by `revyl config migrate`): `pr_review.preset` (`preview_only | proof_on_demand | smoke_every_pr | adaptive_report`), `skip_drafts`, `path_filters`, `label_filters`, `actions.preview_link`, `actions.strict_build_checks`, `actions.proof_of_changes`, `actions.checks` (→ migrated to `always_verify`), `actions.system_prompt`, `actions.proof_harness`, `actions.workflows`, and `builds.ios/android` with `framework` (`expo_ios, expo_android, react_native_ios, react_native_android, native_ios, native_android`), `image`, `app`, `root_dir`, `build_command`, `artifact_path`, `use_existing_ci`, `env`, `secrets`, `caches`. The file comment says it "mirrors the backend schema in cognisim_backend/app/services/scm_config_file.py and the 'generate with AI' prompt". (source code) — [pr_review.go](https://github.com/RevylAI/revyl-cli/blob/main/internal/config/pr_review.go)
- Publishing authority: a project is either `manual` (configured in the web app, pulled with `revyl config pull`, pushed with `revyl config push`) or `git_default_branch` (committing a valid `.revyl/config.yaml` to the default branch "reconciles a matching server project or creates a new Git-managed project … Pull requests validate new configs as unpublished bootstrap candidates; creation occurs only from the actual merged default-branch commit"). `revyl github status --json` returns `{connected, repository_count, repository:{full_name, access_granted}, project:{root, status: not_published|enabled|disabled|not_configured|invalid, authority: manual|git_default_branch, next_action}}`. (source code docs) — [revyl-cli README](https://github.com/RevylAI/revyl-cli#readme), [docs/github-status.md](https://github.com/RevylAI/revyl-cli/blob/main/docs/github-status.md)
- Verdicts **[older, pre 2026-09-18]**: "Passed, Failed, and Inconclusive per build target. Inconclusive: Nothing useful was observed, for example the device never started, or setup blocked the run before the change could be exercised." — [docs: Proof of Changes](https://docs.revyl.com/develop/proof-of-changes)
- Verdicts (current): "Every proof now ends as Ready, Ready with polish, Ready with issues, Failed, or Inconclusive … each write-up scores its confidence from 1/5 to 5/5 and links real problems to their Atlas threads." Same release: `revyl build` now defaults to cloud runners (`--local` keeps it on your machine), iOS push notifications on cloud devices, and a fix for proofs stuck on "Waiting for CI build" on draft PRs. — [changelog 2026-09-18](https://revyl.com/changelog/2026-09-18/)
- "A claimed ready outcome still requires a recorded device session." "A later push replaces the proof for the new commit rather than appending another comment." — [docs: GitHub](https://docs.revyl.com/integrations/github); [docs: Cursor Cloud Agents](https://docs.revyl.com/integrations/cursor/cloud-agents)
- Inside the Revyl sandbox the agent publishes its write-up with the hidden CLI command `revyl proof comment <file> [--problem "…"|--blocked "…"]`: "These commands work only inside an agent Revyl launched to prove a pull request: a Revyl proof sandbox, whose REVYL_API_KEY is minted for that one pull request, or a Cursor cloud agent Revyl dispatched for it … Revyl keeps one comment per pull request and renders your markdown inside it … Inside a Revyl proof sandbox you may post early with what you have and post again as you learn more. A Cursor cloud agent posts once; a later post is rejected (HTTP 409) … Images must be URLs from `revyl session publish`; Revyl refuses the write-up if any other image is present." `--problem` = "the pull request itself is broken", `--blocked` = "you never got to see it run at all"; sending neither "says you watched the change work". (source code) — [cmd/revyl/proof.go](https://github.com/RevylAI/revyl-cli/blob/main/cmd/revyl/proof.go)
- Cursor harness: set `harness.kind: cursor`, then `revyl config authorize-cursor-proof` (or dashboard button "Authorize Cursor proof runs"); "the authorization is stored as live server state, not in YAML. Revyl rechecks the authorizing user's Revyl role and Cursor repository access each time it launches a proof". Findings "land in the same Revyl comment as preview builds", attributed to the Cursor agent with a link to the Cursor thread and an "Open in Cursor" link. — [docs: Cursor Cloud Agents](https://docs.revyl.com/integrations/cursor/cloud-agents); [docs: Cursor cloud getting started](https://docs.revyl.com/guides/cursor-cloud-getting-started). API: `GET/PUT /api/v1/projects/{project_id}/cursor-proof-authorization` (source code: `openapi.json`).

**Path B — BYO CI + coding agent (no GitHub App)**
- Canonical Cursor Automation package in the CLI repo: CI builds → `revyl build upload --version "${{ github.event.pull_request.head.sha || github.sha }}"` → Automation triggers on "CI completed / Workflow run completed" → agent matches the build to the PR head SHA via `revyl build list --app <id> --json` (`metadata.scm_head_sha`, `metadata.git.commit`, or version string) → `revyl device start --build-version-id <id> --json` → drive app with `revyl device screenshot` / `revyl device validation` → `revyl device stop` → `revyl device report --session-id <id> --json` → `revyl session share <id> --json` (shareable_link, no Revyl login needed) → `revyl session publish <file> --session <id> --json` (public_url for images) → one PR comment headed `## Revyl device proof`. "If there is still no matching build, stop. Post a short PR comment … stating that no Revyl build for this commit is available yet, and that proof was not run. Do not invent a build id." (source code) — [examples/cursor-automation/prove-mobile-pr/PROMPT.md](https://github.com/RevylAI/revyl-cli/blob/main/examples/cursor-automation/prove-mobile-pr/PROMPT.md); [docs: Cursor proof](https://docs.revyl.com/guides/cursor-proof)
- Agent-driven GitHub Actions example with Claude Code: `on: pull_request [opened, synchronize, reopened]` + `issue_comment` containing `/review`; steps install CLI via `curl -fsSL https://revyl.com/install.sh | sh`, then `anthropics/claude-code-action@v1` with `direct_prompt: "You are a mobile PR review bot. Read CLAUDE.md for instructions."`, `allowed_tools: "Bash,Read,Glob,Grep,Write"`, env `REVYL_API_KEY`, `REVYL_APP_ID`. (source code) — [examples/pr-review/agent-driven.yml](https://github.com/RevylAI/revyl-cli/blob/main/examples/pr-review/agent-driven.yml)
- Comparison table in that README: Agent-driven = "Exploratory, visual validation of UI changes", requires Anthropic API key + playbook, "Slower (agent explores)", coverage "Adapts to what changed"; CLI-driven = "Regression testing with known test flows", "Faster (runs known steps)", "Fixed test suite". — [examples/pr-review/README.md](https://github.com/RevylAI/revyl-cli/blob/main/examples/pr-review/README.md)

**Path C — official GitHub Actions**
- `RevylAI/revyl-gh-action` ships three composite actions: `upload-build`, `run-test`, `run-workflow`. `run-test` inputs: `test-id` | `workflow-id`, `retries` (1–5, default 1), `build-id`, `branch`, `all-branches`, `timeout` (default 3600 s), `no-wait`, `backend-url` (default `https://backend.revyl.ai`), `dashboard-url` (default `https://app.revyl.ai`), `cli-version` (default `latest`). Outputs: `success`, `task_id`, `report_link` ("Shareable link to the detailed test execution report"), `execution_time`, `platform`, `error_message`, `total_steps`, `completed_steps`, `total_tests`, `completed_tests`, `passed_tests`, `failed_tests`. Monitoring is via Server-Sent Events ("v2.0.0 … Real-time monitoring via Server-Sent Events" replacing v1 polling). (source code) — [run-test/action.yml](https://github.com/RevylAI/revyl-gh-action/blob/main/run-test/action.yml), [run-test/README.md](https://github.com/RevylAI/revyl-gh-action/blob/main/run-test/README.md)
- Raw upload API: `curl -X POST "https://backend.revyl.ai/api/v1/apps/{APP_ID}/builds/stream-upload?version={VERSION}" -H "Authorization: Bearer $REVYL_API_KEY" -F "file=@./app.apk"` → `{id, version, package_name, artifact_url, metadata:{package_id, artifact_bytes, artifact_sha256}}`. (source code) — [revyl-gh-action README](https://github.com/RevylAI/revyl-gh-action#readme)
- Example `pr-tests.yml`: `uses: RevylAI/revyl-gh-action/run-workflow@v2.0.5` with `workflow-id`. (source code) — [examples/ci-github-actions/pr-tests.yml](https://github.com/RevylAI/revyl-cli/blob/main/examples/ci-github-actions/pr-tests.yml)
- Other CI recipes shipped in the CLI repo: Jenkinsfile, CircleCI, GitLab CI, Screwdriver; GitLab automation via `revyl gitlab setup`. — [examples/ci-generic](https://github.com/RevylAI/revyl-cli/tree/main/examples/ci-generic), [revyl-cli README](https://github.com/RevylAI/revyl-cli#readme)

### Inferences
- Verdict → GitHub mapping: the docs only define a failing *check* for failed managed builds (`strict_ci_check.build`); the proof verdict itself appears to be delivered as a rendered comment block, not as a required status check. (No source found stating that Inconclusive/Failed proofs set a GitHub check.)
- The `proof` CLI group being hidden and bound to a per-PR minted API key implies the hosted agent runs the *same* `revyl` CLI inside its sandbox that users run locally; the backend's `cognisim_backend` is the private orchestrator.

### Gaps
- Exact rendered layout of the Revyl GitHub comment block (headings, badges) for the hosted path was not retrievable (docs blocked); only the Cursor/BYO-CI `## Revyl device proof` template is verified from source.
- Whether an Inconclusive or Failed *proof* creates a failing GitHub check or blocks merge: not documented in sources found.
- Which LLM(s) the hosted Revyl harness uses: not disclosed (the `model_id` option exists only for the Cursor harness).

## Key Question 2 — How the agent obtains PR/task context (diff, PR body, tickets, Figma) and decides what to test

### Takeaway
The PR **diff is authoritative**; the PR description is a bounded, author-written excerpt used only as supporting context (and only in the Revyl harness); `always_verify` adds standing natural-language invariants; `system_prompt` adds team guidance. There is **no Jira/Linear ticket ingestion** and **no Figma input to Proof of Changes** (Figma comparison exists only as a separate Atlas-based review skill). Flow selection (diff hunks → screens) is an opaque LLM decision in the hosted product; in the open-source templates it is explicitly "read the diff, form a one-sentence hypothesis, drive the device reactively".

### Cited Findings
- "The agent uses a bounded excerpt of the author-written part of the PR description as context for intent, expected behavior, and a proposed test plan. The diff and any configured `always_verify` checks stay authoritative." — [docs: Proof of Changes](https://docs.revyl.com/develop/proof-of-changes)
- "The pull-request diff supplies the change-specific proof intent. The PR description is only available as supporting context when the Revyl harness is used." `always_verify` are "natural-language invariants checked on every run in addition to the diff, meant for things that must always hold, not as a replacement for inspecting the change." Example invariants in docs: launching to the home screen and logging in with email. — [docs: GitHub](https://docs.revyl.com/integrations/github)
- Cursor/BYO-CI prompt (source code): "Read the pull request diff and verify the behaviour it changes. That is the primary source of checks. If the repository also lists invariants that must hold on every run (configured checks, playbook entries, or similar), verify those in addition … never instead of it. Treat the pull request description, including any bot-generated summary, as context rather than authoritative proof of intended behaviour. Do not accept surprising or broken behaviour as intentional solely because the description says it is; require support from concrete requirements, tests, or code semantics." — [PROMPT.md](https://github.com/RevylAI/revyl-cli/blob/main/examples/cursor-automation/prove-mobile-pr/PROMPT.md)
- Existing findings are inputs too: "Before deciding what to test, run `revyl report annotations list --json` and treat every open result, including findings created by humans or on earlier pushes, as part of this review … Reply … or resolve … instead of creating a duplicate." — [PROMPT.md](https://github.com/RevylAI/revyl-cli/blob/main/examples/cursor-automation/prove-mobile-pr/PROMPT.md)
- Open-source PR reviewer (mobile-pr-reviewer `CLAUDE.md`): step 1 "Analyze the PR" = `git diff "origin/$PR_BASE_REF"...HEAD --stat`, then diff restricted to `'*.tsx' '*.ts' '*.jsx' '*.js' '*.swift' '*.kt' '*.xml'`, plus `gh pr view … --json title,body`; "Form a one-sentence hypothesis about what to validate", e.g. "Cart should contain Orchid Mantis at $62 after tapping ADD TO CART". Scope rule: "Focus on user-visible changes — UI, text, navigation, styling. Ignore test-only changes, configs, and dep bumps unless they affect the UI. If the diff is huge, pick the most impactful screen and validate that." (source code) — [mobile-pr-reviewer/CLAUDE.md](https://github.com/RevylAI/mobile-pr-reviewer/blob/main/CLAUDE.md)
- Same template deliberately avoids Revyl's planner: "You never call `revyl device instruction` or `revyl device validation`. Those are higher-level helpers that use Revyl's planner; this template is built around the lower-level primitives so Claude does the planning." Loop: screenshot → Read PNG → one action → wait 1–3 s → repeat; stop when validated, bug reproduced, or "three consecutive screenshots show the same screen". — [mobile-pr-reviewer/CLAUDE.md](https://github.com/RevylAI/mobile-pr-reviewer/blob/main/CLAUDE.md)
- mobile-devtools summary of that bot: "When a developer opens a PR, Claude reads the diff, figures out what changed, boots a cloud device with the new build, navigates to the affected screen, and posts screenshot evidence directly in the PR … Understands code diffs to determine what screens to test … Posts before/after screenshots as PR comments". (Note: the current `mobile-pr-reviewer` repo instead posts only the recording link — see KQ4.) — [mobile-devtools README](https://github.com/RevylAI/mobile-devtools#readme)
- App context the team supplies: `CLAUDE.md` playbook with App name, platform, bundle ID, "Key screens", and PR comment format; in the hosted product, `pr_review.proof_of_changes.system_prompt`. (source code) — [agent-playbook.md](https://github.com/RevylAI/revyl-cli/blob/main/examples/pr-review/agent-playbook.md)
- Figma: a separate skill `revyl-cli-figma-review` compares Figma frames/components against **Atlas** screenshots ("Existing Atlas captures are sufficient to start; no app checkout or new device session is required … Visual comparison does not establish which code component or token was used"). It is a local-agent workflow, not part of Proof of Changes. — [docs/figma-review.md](https://github.com/RevylAI/revyl-cli/blob/main/docs/figma-review.md)
- Competitor critique: "no Jira sync or test-case management layer". — [TestMu AI comparison](https://www.testmuai.com/revyl-alternative/) (competitor page; treat as biased)

### Inferences
- The "proposed test plan" extracted from the PR body suggests the hosted agent produces an explicit plan before driving; combined with per-build-target proof runs, each target likely gets its own plan + write-up.
- Because the sandbox has a repo checkout, the hosted agent can also read source files beyond the diff (the Cursor prompt says "You are already in Cursor's checkout of this pull request"), but no source states that it statically traces diff → screen mapping.

### Gaps
- No documentation of how diff hunks are mapped to screens/flows (e.g. via Atlas graph lookup) in the hosted harness.
- No support found for Jira/Linear/Figma as Proof-of-Changes inputs.

## Key Question 3 — What is Atlas, what evidence does Revyl collect, and what does a report look like?

### Takeaway
Atlas is a **media-grounded knowledge graph of the app built from observed runs**: nodes are screen clusters (with variants/observations), edges are observed transitions (with video clip intervals and originating report IDs), plus product-area groupings, "heat", and annotation threads (findings). Every test, exploration, dev session or proof run feeds it. Per-run **reports** contain video + step timeline + AI summary + per-step/action results and reasoning + device logs + network + CPU/FPS/memory (+ Perfetto on Android) + device-state snapshots, all addressable by CLI/JSON.

### Cited Findings

**Atlas**
- "Atlas turns observed test and session activity into a searchable graph of screens, variants, and transitions … groups similar screens together even when the content changes." Views: Map (flow graph) vs Grid; toggles "Show variants", "Heat" (frequently observed screens/paths), "Clusters" (product-area groupings); details panel "shows screenshots, variants, evidence, and incoming and outgoing transitions". Default scope = "Current map, which is built from the 20 most recently uploaded builds". — [docs: Atlas](https://docs.revyl.com/atlas)
- "Every time an agent or person uses a Revyl device on your app, whether in a test, an exploration, or a development session, the screens and transitions it sees are added to Atlas." "Explorations are agents that drive Revyl phones through your app to map it." — [Atlas overview and CLI guide](https://revyl.com/guides/atlas-overview-and-cli/)
- Public gallery examples: LinkedIn map "61 iOS app screens, 62 transitions, 38 user paths, and 568 UI elements"; Uber "71 screens and 20 user paths". — [revyl.com/atlas/linkedin](https://revyl.com/atlas/linkedin/), [revyl.com/atlas/uber](https://revyl.com/atlas/uber/)
- CLI model (source code docs): "Screens are nodes and observed relationships are edges … Everything in Atlas originated in observed run evidence. Generated names and grouping are interpretations." Commands: `revyl atlas apps|brief|graph|map|search <q>|screen <id>|observations <id>|observation <id>|report <screen-or-observation-id>|neighbors <id>|edge <src> <dst> --runs|area <product-area>|open`, with `--branch/--build/--all-branches`, `--device-model`, `--runtime`, `--screenshots --screenshot-dir`. `graph` returns `starting_anchors` (`curated_entry | semantic_entry | observed_root`), `nodes`, typed edges, `truncated/has_more`. `edge --runs --json` gives the newest run's `active_video.video_url`, `source_video_start`, `source_video_end`, `execution_id`, `session_id`. — [docs/atlas.md](https://github.com/RevylAI/revyl-cli/blob/main/docs/atlas.md)
- Atlas REST surface (source code `openapi.json`): `GET /api/v1/atlas/v2/apps/{app_id}/graph`, `/structure`, `/edge-runs`, `/entities/{entity_id}/observations`, `/observations/{observation_id}`, annotation threads (`grounded-annotation-threads`, `annotation-anchor-preview`, `/annotation-threads/{id}/replies|resolve|dismiss|reopen|severity|anchor`), `GET /api/v1/atlas/v2/index`. — [openapi.json](https://github.com/RevylAI/revyl-cli/blob/main/openapi.json)
- Atlas comments/findings: since 2026-08-21 "teammates can comment on Atlas screens"; "You can embed a live cloud device on any web page … added Explore from the CLI." — [changelog 2026-08-21](https://revyl.com/changelog/2026-08-21/)
- Findings used in PR proofs are Atlas annotation threads created from the device session: `revyl report annotations create --dry-run --target "the save button" --preview-out <png> --preview-receipt-out <json>` then `revyl report annotations create --body-file <md> --preview-receipt <json> --severity issue`; severities `blocker | issue | polish`; `annotations list|reply|resolve|severity`. "findings render on the pull request as you create them; the write-up is the narrative around them." (source code) — [PROMPT.md](https://github.com/RevylAI/revyl-cli/blob/main/examples/cursor-automation/prove-mobile-pr/PROMPT.md)
- Exploration API: `POST /api/v1/explorations/apps/{app_id}`, `GET /explorations/{run_id}`, `/report`, `/cancel`. CLI: `revyl explore run "My App" --branch staging --explorers 1 --strategy surface-sweep|balanced|journey-focus|hard-edges --instructions "Cover checkout…" --max-duration 20m --timeout 35m --auth-instructions … --launch-var …`. "Uploading alone doesn't populate Atlas." (source code) — [docs/explore.md](https://github.com/RevylAI/revyl-cli/blob/main/docs/explore.md)

**Reports / evidence per run**
- Report UI: "Each run gets a full video recording and a step-by-step timeline … video and timeline on the left and a five-tab inspector on the right." Summary tab = AI overview with key moments that seek the video and failure call-outs; Performance tab = CPU, FPS, memory + device logs synced to video, step executions as shaded regions, failures red, Android can export a Perfetto trace; Device logs filterable/searchable; network requests exportable as JSON; Info tab = execution, app/build, device info, test/execution/trace IDs. — [docs: Reports](https://docs.revyl.com/tests/reports)
- Core concept list: Report "includes pass/fail status, video replay, AI summary, device logs, and network activity." Session: "a live device instance … Convert to test on the session row turns your interactions into structured test steps." — [docs: Core Concepts](https://docs.revyl.com/get-started/concepts)
- Programmatic evidence (source code docs): `revyl device report --session-id <id> --json`, `revyl test report <name|execution-id> --json`, `revyl run inspect <uuid> --id-kind session --section overview|steps|actions|field --step-id --action-id --status failed --grep`; field pointer `/reasoning` on an action returns the agent's per-action reasoning; `reports.logs` (grep/level/tail/context), `reports.network` (min_duration_ms, slowest_first), `reports.performance`, `reports.state`. "Full LLM call payloads are excluded." ## Key Question 5 — Visual verification, grounding, self-healing, test generation from exploration, device/OS matrix, build upload

### Takeaway
Revyl is vision-first: every step is capture → ground (a UI-grounding vision model proposes pixel coordinates for a natural-language target) → act (UIAutomator/XCTest-level execution) → verify (judge new screenshot). "Self-healing" in Revyl's vocabulary means no selectors to break, not automatic test rewriting. Tests can be generated from a recorded session (`revyl test create --from-session`) or from Explore runs. Devices are **cloud iOS simulators and Android emulators only** (no physical devices), with a documented iOS 18.5–27.0 matrix and a thin Android matrix (Pixel 7 / Android 14 in the CLI target file). Builds arrive via Revyl cloud builds, CLI/API upload, or Expo EAS auto-sync.

### Cited Findings
- "Each step runs capture, ground, act, and verify. … a vision model tuned for UI grounding takes the screenshot plus a natural-language target like 'place order' and proposes pixel coordinates … capture the new screen and judge whether the step did what it was supposed to." Accessibility trees are "unreliable on many production apps", so Revyl "locates elements from the rendered screen"; admits it "costs more time and compute than reading a value straight out of a node". — [blog: Why Revyl Tests by Sight](https://revyl.com/blog/why-revyl-tests-by-sight/)
- "A reasoning model understands intent and a vision model locates the element on screen. When grounding fails, the system retries with expanded search regions." Stack: "vision models for screen understanding, BAML for structured LLM interactions, and platform-specific automation (UIAutomator2, XCTest)". Difficulties: "vision models hallucinate coordinates, screen densities vary across devices, and dynamic UIs shift elements between capture and execution." — [blog: understanding AI grounding](https://revyl.com/blog/understanding-ai-grounding/), [blog: mobile infra for coding agents](https://revyl.com/blog/mobile-infra-for-coding-agents/)
- Backend grounding endpoint exists: `POST /api/v1/execution/ground`; device actions proxied via `GET/POST /api/v1/execution/device-proxy/{workflow_run_id}/{action}`; `POST /api/v1/execution/start_device`; `GET /api/v1/execution/device-targets`. (source code) — [openapi.json](https://github.com/RevylAI/revyl-cli/blob/main/openapi.json)
- Self-healing (marketing): "visual recognition that can identify UI elements even when their underlying code changes"; infra sense: pipelines "auto-restart on codec failures without losing the session". Revyl says its approach "avoids selectors, so each step is written in plain language and checked with a vision model". — [blog: AI transforming mobile testing 2025](https://revyl.com/blog/ai-transforming-mobile-testing-2025/), [blog: fix flaky iOS tests](https://revyl.com/blog/fix-flaky-ios-tests/)
- Test generation: "an exploratory session can be turned into a regression test with `revyl test create --from-session`"; dashboard "Convert to test" on a session row; CLI `revyl test create --from-session <session-id> <name> --app <app-id>` ("The name can be omitted; the compiler will use its suggested session title"); YAML endpoint `POST /api/v1/tests/yaml/from-blocks`. — [docs: Managing Tests](https://docs.revyl.com/cli/tests), [skills/revyl-cli-create](https://github.com/RevylAI/revyl-cli/blob/main/skills/revyl-cli-create/SKILL.md), [openapi.json](https://github.com/RevylAI/revyl-cli/blob/main/openapi.json)
- Devices: "Revyl runs tests on cloud simulators (iOS) and emulators (Android), not physical devices"; iOS builds "must target the simulator SDK. An iOS distribution archive cannot be installed into a simulator"; Android needs "an installable APK with a supported ABI" (no .aab). Marketing pages inconsistently say "real iOS and Android devices". — [docs: Artifact Requirements](https://docs.revyl.com/builds/artifact-requirements), [pricing](https://revyl.com/pricing/)
- Device provisioning: "iOS simulators are erased between runs for isolation, then booted and connected to a companion daemon. Pre-warming cuts first-task latency"; request path "agent → Revyl API → orchestrator → device pools → device action → WebRTC stream → verified result". Blog table claims "10,000+ max concurrent sessions"; enterprise page promises "hundreds of concurrent cloud device sessions … without queues" (unreconciled). — [blog: mobile infra](https://revyl.com/blog/mobile-infra-for-coding-agents/), [enterprise](https://revyl.com/solutions/teams/enterprises/)

- Builds: `revyl build --profile <name> --platform ios|android [--local|--remote] [--env] [--secret] [--image] [--no-cache] [--pin] [--branch]` runs on cloud runners by default; `revyl build upload --file … --app … --platform … --version … [--skip-build] --yes --json`; `POST /api/v1/apps/remote` (remote build job), `/apps/{app_id}/builds/upload-url|upload-session|multipart-upload/start|from-url`. Toolchain images: "Each remote build runs on an image that sets the OS plus Xcode or the Android SDK. Image selection follows a fixed precedence: an explicit flag, then the recipe's image, then the platform default." Expo: EAS webhook auto-import (Robot User token; iOS profile needs `"simulator": true`; Android only debuggable .apk; production profiles excluded). Fingerprinting: "@expo/fingerprint … reuse an earlier app build and update only the JavaScript when native code hasn't changed" (2026-08-07: "JavaScript-only Expo changes reuse existing native artifacts"). — [README](https://github.com/RevylAI/revyl-cli#readme), [docs: Toolchain Images](https://docs.revyl.com/remote-builds/toolchains), [docs: Expo Auto Sync](https://docs.revyl.com/builds/expo-sync), [docs: Fingerprinting](https://docs.revyl.com/remote-builds/fingerprinting), [changelog 2026-08-07](https://revyl.com/changelog/2026-08-07/)

- Verification of a "validation" step is itself an LLM judgement over a screenshot (the `validation` block / `revyl device validation <description>` returns `validation_result: bool`), so "visual verification" = VLM assertion, not pixel comparison; pixel diffing exists only in the open-source visual-regression / Figma tools.
- Android coverage appears far thinner than iOS (one emulator model/runtime in the CLI's target file), though docs mention "Pixel and Samsung emulators" and an "Android 15 Pixel 9 Pro" example run — the shipped target file may lag the backend.

## Key Question 6 — How tests are authored (natural language / YAML / recorded), caching & determinism, flakiness handling

### Takeaway
Tests are YAML (`.revyl/tests/<name>.yaml`, committed as source of truth) with typed blocks whose payloads are natural-language `step_description`s: `instructions`, `validation`, `extraction`, `manual`, `code_execution`, `module_import`, `if`, `while`; variables via `{{name}}` / `{{global.name}}`; or authored in the web editor / converted from a recorded session. Determinism is handled by test-only launch flags, erased simulators, auth bypass, `--retries`, and a Stability classification (stable / flaky / broken); build caches are per-clean-VM compilation caches (on by default) plus opt-in path caches.

### Cited Findings
- YAML schema: root `test` with `metadata` (name, platform, tags), `build` (app name), `variables`, ordered `blocks`; "Every block uses an explicit `type:` field plus a `step_description:` payload." Block types `instructions` ("A single user action (tap, type, swipe)"), `validation` ("assertions about the expected state after an action"), `extraction` (stores into `variable_name`), `if`/`while`/`module_import`. Guidance: "Keep each step to one action or one assertion." — [docs: YAML Test Format](https://docs.revyl.com/appendix/yaml-test-format)
- Example (source code):
  ```yaml
  test:
    metadata: {name: login-flow, platform: ios}
    build: {name: my-app-ios}
    blocks:
      - type: instructions
        step_description: "Tap the 'Sign In' button on the welcome screen"
      - type: validation
        step_description: "The home screen is visible with a welcome message"
  ```
  and control flow `- type: if` / `condition: "An onboarding or welcome modal is visible"` / `then:` / `else:`; `- type: while` / `condition: "Fewer than {{max-items}} products …"` / `body:`. — [examples/yaml-tests](https://github.com/RevylAI/revyl-cli/tree/main/examples/yaml-tests)
- Additional block types from the authoring skill: `manual` (framework actions `wait, go_home, navigate, set_location, kill_app, open_app`), `code_execution` (saved script or inline; `revyl script create seed-user --file scripts/seed_user.py --runtime python`), `module_import` (reusable block groups: `revyl module create/list/get/update/usage/insert`). Secrets: `revyl global var set login-password='secret' --secret` → `{{global.login-password}}`; launch env: `revyl global launch-var create API_URL=…`. — [skills/revyl-cli-create/SKILL.md](https://github.com/RevylAI/revyl-cli/blob/main/skills/revyl-cli-create/SKILL.md)
- Authoring loop: `revyl test validate my-test.yaml` → `revyl test create <name> --from-file <file>` → edit → `revyl test push <name> --force` → `revyl test run <name> [--open|--no-open] [--retries n] [--timeout s] [--no-wait] [--json] [--build-version-id id] [--build]` → `revyl test report <name> --json`; `revyl test list`, `revyl test cancel <task_id>`, `revyl test open <name>` (browser editor); workflows `revyl workflow create smoke-tests --tests login-flow,checkout`, `revyl workflow run smoke-tests`. "The .revyl/tests/ directory is not gitignored by default. These YAML files are your source of truth — commit them." ## Appendix A — Verified end-to-end sequence (hosted Revyl GitHub App path), assembled from the citations above

1. Team installs the Revyl GitHub App (dashboard or `revyl github connect`), runs `revyl init` + `revyl github setup`, and commits `.revyl/config.yaml` to the default branch (or publishes manually via `revyl config push`). Policy keys: `pr_review.enabled`, `review_triggers.{paths,labels,drafts}`, `build.{kind: revyl|ci_upload_to_revyl, profile|app_ids}`, `proof_of_changes.{enabled, harness.kind, system_prompt, always_verify[]}`, `workflow_ids[]`, `strict_ci_check.build`, plus `session.{auth_bypass, before_script}` and `build.profiles.<name>.<platform>.{setup_commands, build_commands, output_path, image, timeout_seconds, env, secrets, caches}`.
2. PR opened/synchronized (filters applied; drafts skipped unless `drafts: true`). Revyl reads the config *from the PR's commit*.
3. For each configured build target: Revyl cloud-builds the PR (clean VM, toolchain image, caches) or waits for a CI upload whose metadata (`scm_head_sha`/`pr_number`) matches; a failed managed build can emit a failing GitHub check (`strict_ci_check.build`). A preview link/live-device embed is posted.
4. Proof: the Revyl agent (or an authorized Cursor cloud agent) gets a disposable checkout of the PR + a per-PR minted `REVYL_API_KEY`; reads the diff (authoritative), a bounded excerpt of the author-written PR body (context/proposed plan), `system_prompt`, and `always_verify`; starts a cloud simulator/emulator on the exact build (`revyl device start --build-version-id …`, with auth-bypass launch vars and before_script applied); drives the app via grounded natural-language actions and `validation` judgements; captures screenshots (`revyl session publish` → https URLs), and may create Atlas-anchored findings (`revyl report annotations create … --severity blocker|issue|polish`), reconciling pre-existing open findings.
5. Verdict: `Ready | Ready with polish | Ready with issues | Failed | Inconclusive` per build target, confidence 1/5–5/5, rendered into a single Revyl comment block (replaced on each new push) via `revyl proof comment <md> [--problem|--blocked]`, with a shareable session report (video, step timeline, logs, network, perf). Optional saved `workflow_ids` regression runs are reported in the same block. A "ready" claim requires a recorded device session.

## Appendix B — Verified sequence for the open-source/BYO-CI path (what a clone can replicate today)

`pull_request` workflow → build artifact (simulator `.app`/`.app.zip` or debuggable `.apk`) → `revyl build upload --version <head sha> --json` (CI metadata stamped) → coding agent (Claude Code Action / Cursor Automation) with a `CLAUDE.md` playbook: `git diff origin/$PR_BASE_REF...HEAD` → hypothesis → `revyl device start --build-version-id … --json` → loop `revyl device screenshot --out … ; Read PNG ; revyl device tap|type|swipe --target "…" --json` (fallback `--x --y` only for system dialogs; stop after 3 identical screenshots) → `revyl device stop --all --json` → `revyl device report --session-id … --json`, `revyl session share`, `revyl session publish` → one PR comment (`## 📱 Mobile PR Review` or `## Revyl device proof`, edited in place on re-runs) containing hypothesis, observations, ✅/❌ (+ Expected/Observed), recording link, optional `<img width="220">` thumbnails in a `<table>`; never claim proof without a device session; comment "proof was not run" if no build matches the head SHA.
