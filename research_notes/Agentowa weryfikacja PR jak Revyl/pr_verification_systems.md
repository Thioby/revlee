## KQ1. Does a fully agentic open-source "read PR + linked issue → generate test plan → drive the app → post verdict/evidence to the PR" system exist?

### Takeaway
No mature open-source project does the full loop end-to-end (ticket/acceptance criteria → test plan → real browser/device execution → evidence posted to the PR). The closest open-source pieces are (a) Revyl's MIT-licensed `mobile-pr-reviewer` (Claude Code Action + Revyl cloud devices; reads the diff, taps through the app, posts a recording link — no ticket input, no pre-written plan), (b) `ACHultman/pr-qa-copilot` (MIT GitHub Action; finds the preview deployment, runs Playwright journeys from a JSON file + changed Next.js routes, posts one idempotent comment + artifact — journeys are hand-written, LLM is optional and only for a summary), (c) agent skills/prompts (Shiplight `verify`, Claude Code bundled `/verify`, Playwright 1.56 planner/generator/healer agents, OpenHands `qa-changes`/`iterate`) which verify locally but do not implement the PR→ticket→evidence loop. The academic SWE-Review (July 2026) formalizes "issue + PR → reviewer agent accept/reject" but is code-review, not app execution.

Android/iOS run in parallel via `strategy.matrix.platform`; builds via `./gradlew assembleDebug` / `xcodebuild -scheme MyApp -sdk iphonesimulator`. Model via `claude_args: --model claude-sonnet-4-5`. ### Inferences
- The open-source state of the art is "coding-agent + browser/device CLI + prompt" (mobile-pr-reviewer, Shiplight verify, /verify). None reads Jira/Linear acceptance criteria, none produces a structured traceable test plan, and none posts a check run with structured evidence. A system that does all of that would be new in open source.
- The mobile-pr-reviewer design (reactive screenshot→act loop, no plan, Revyl-hosted recording link) is the closest template for a Revyl-style mobile verifier but it is tiny (5 stars) and is a Revyl-authored demo of Claude Code Action rather than a product.
- pr-qa-copilot shows the practical GitHub plumbing (Deployments API for preview URL, idempotent comment, artifacts, Vercel bypass) that an agentic verifier needs, but keeps the test plan deterministic.

### Gaps
- Could not read `mobile-pr-reviewer`'s `review.yml`/`CLAUDE.md` (page shows README only); exact prompt, permissions and how the "recording link" is generated are unknown.
- Could not confirm whether `revyl-codex-proof-ci` / `revyl-proof-automation` exist in any public repo (catalog listings only).
- Could not inspect OpenHands `qa-changes` plugin SKILL.md (404 on directory fetch).

## KQ2. Built-in verification in coding agents (Codex, Copilot coding agent, Devin, Claude Code): what they read, whether they run the app, platforms, how results are posted

### Takeaway
All four major coding agents now verify *their own* changes by running the app (Copilot: Playwright MCP browser with screenshots in the PR since July 2025; Devin: post-PR "testing mode" with annotated screen recordings since ~late 2025/2026; Codex: in-app browser on localhost since April 2026 plus `@codex review`; Claude Code: `/verify` + Chrome extension). None of them is offered as a standalone "verify someone else's PR against its ticket" service; verification is a side-effect of the agent authoring the PR, evidence is attached as PR screenshots or chat attachments, and none posts a GitHub check run.

### Cited Findings
- **GitHub Copilot coding agent (2 Jul 2025 changelog):** "Copilot coding agent now has its own web browser" via the Playwright MCP server, enabled by default together with the GitHub MCP server; "This allows Copilot to reproduce bugs and validate its work. Copilot can also post screenshots in its pull request"; public preview for all paid Copilot plans. Microsoft dev blog (7 Aug 2025): "Assign an issue to Copilot Coding Agent, and it uses Playwright MCP to verify its work in a real browser." Environment customization via `.github/workflows/copilot-setup-steps.yml` (single `copilot-setup-steps` job, must be on default branch; "If a custom setup step fails, Copilot will start working anyway"); self-hosted runners supported since 28 Oct 2025; agent firewall can be disabled/customized. — [github.blog changelog 2025-07-02](https://github.blog/changelog/2025-07-02-copilot-coding-agent-now-has-its-own-web-browser/); [developer.microsoft.com blog](https://developer.microsoft.com/blog/the-complete-playwright-end-to-end-story-tools-ai-and-real-world-workflows/); [docs: customize agent environment](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-environment); [changelog 2025-07-30 setup steps](https://github.blog/changelog/2025-07-30-copilot-coding-agent-custom-setup-steps-are-more-reliable-and-easier-to-debug); [changelog 2025-10-28 self-hosted](https://github.blog/changelog/2025-10-28-copilot-coding-agent-now-supports-self-hosted-runners). Argos (vendor) critique: agent in-session screenshots are "point-in-time and not auditable" — [argos-ci.com blog](https://argos-ci.com/blog/playwright-mcp-visual-testing)
- **Devin (Cognition) testing mode (official docs):** "After creating a PR, Devin will offer to test the app for you. Click Test the app"; "A setting to automatically run testing after PR creation is coming soon"; three phases: setup (installs deps, starts services, logins, "Checks for relevant skills in the repo (under .agents/skills/) and follows them if found"), plan ("reads the diff and codebase to create a minimal, focused test plan"), execute ("starts a screen recording, executes the test plan in the desktop, and annotates key moments... sends it to you as a message attachment"). Sample test skill (German page): read git diff to find changed pages, open each, screenshot at 1280px and 375px, check console errors/layout. — [docs.devin.ai testing-and-recordings](https://docs.devin.ai/work-with-devin/testing-and-recordings); [German version](https://docs.devin.ai/de/work-with-devin/testing-and-recordings)

- **Devin Review:** "code review tool that uses state-of-the-art AI + UX to scale human understanding of ever-more-complex code diffs"; free in early release; swap "github"→"devinreview" in a PR URL; Devin 2.2 added "screen-recorded testing for desktop applications, along with self-review and autofix before a human opens the PR". - **Claude Code GitHub app / action:** see KQ1 — comments only, no formal review/approval, no check runs, Bash must be allowlisted.

### Inferences
- The coding-agent vendors treat runtime verification as part of *authoring* (closing the loop on their own PR) rather than as an independent gate on arbitrary PRs; the GitHub surface used is a PR comment/description with screenshots (Copilot) or an out-of-band attachment (Devin). This leaves room for an independent "verifier" that treats the PR + ticket as input regardless of who wrote it.
- Cognition's published failure modes (over-testing, hallucinated paths, lying about findings) and mitigations (ground plan in code first, annotate expectation before action, per-assertion passed/failed/untested) are the most concrete design guidance found for an agentic verifier.

### Gaps
- Could not read Cognition's full post (parallel-Devin / dev-server numbers unverified).
- No official OpenAI documentation found confirming that Codex *cloud* tasks get a browser/screenshots; only desktop-app browser is documented.
- Current (Oct 2026) default-on status of Copilot's Playwright browser not re-confirmed beyond the 2025 changelog.

## KQ3. Commercial AI QA / testing platforms that run the app on PRs (web + mobile): context read, execution, posting

### Takeaway
A cluster of commercial products now does "PR opened → detect preview deployment → agent plans tests from PR title/description/diff (and, for QA.tech, the linked Jira/Linear ticket) → run in a real browser → post a PR review/comment with pass/fail + screenshots/video". The clearest implementations are QA.tech (GitHub App; approve/decline review; grounds every suggested test in a diff hunk; fetches linked Linear/Jira ticket), TesterArmy (planning phase from PR title/description/diff → ordered step table in the PR comment, updated in place; neutral "Tests skipped" when no user-visible change), Autonoma (Replay trace + video + screenshots + network/app logs in the PR comment), Momentic (explore agent drafts tests from the diff; GitHub App comment), Greptile TREX (writes/runs tests in a sandbox, attaches logs/screenshots/videos). Mobile is far thinner: Revyl (cloud iOS/Android devices, Revyl Bot code-review integration, `$29/dev/month` Cloud tier), Maestro Cloud (PR status check, paid plan), TesterArmy (mentions mobile simulator). Octomind reportedly shut down (service end May 2026; single secondary source).

### Cited Findings
- **QA.tech (GitHub App, GitHub-only):** "analyzes the diff, identifies user-facing changes, creates tests for new functionality, runs them against your preview deployment, and posts the results as a review on the PR" with "approval or decline"; "when a PR references an issue tracker ticket (Linear, Jira), the agent fetches that ticket automatically so the review is grounded in the requirement, not just the diff" (changelog 22 Apr 2026 "Code-aware PR reviews powered by the Assessment Agent"); "Every test the agent suggests on a PR must cite a specific file, hunk, or symbol from the change... ## KQ4. Code-review agents with ticket context and/or runtime verification (Qodo, CodeRabbit, Bugbot, Greptile, Augment, Ellipsis)

### Takeaway
Ticket-aware review is mainstream (Qodo Merge pulls Jira/Linear/Azure DevOps/GitHub Issues tickets by PR link or branch name and rates "Fully/Partially/Not compliant"; CodeRabbit assesses the PR against linked-issue requirements; Augment has a Jira/Linear "PR spec adherence" workflow scoring each criterion met/partial/missing). ## KQ5. Patterns for extracting acceptance criteria from issues/tickets and mapping to test steps ("requirements traceability")

### Takeaway
Observed patterns: (1) ticket discovery by PR-body link or branch-name regex (Qodo; GitHub `Closes #N` convention in skills), (2) pulling description + AC field + subtasks + labels (Qodo; AC often lives in a Jira custom field), (3) per-criterion scoring met/partial/missing (Augment, IRA, dev-loops "judge"), (4) one-criterion→≥1-scenario mapping in a plan file with results in an in-place-updated comment (agent-station spec), (5) Jira test-management AI (TestCollab, AgileTest, TestGrid, BrowserStack) generating steps + expected results linked back to the story for a traceability matrix. Devin and TesterArmy derive plans from the diff/PR text rather than the ticket.

### Cited Findings
- Qodo link detection and fields (see KQ4) — [docs.qodo.ai ticketing-integrations](https://docs.qodo.ai/code-review/qodo-merge/integrations/ticketing-integrations)
- QA.tech fetches referenced Linear/Jira ticket "so the review is grounded in the requirement, not just the diff" and requires every suggested test to cite a file/hunk/symbol — [qa.tech changelog 2026-04-22](https://qa.tech/changelog/2026-04-22.md)
- dev-loops `judge` agent "scores each review finding against a linked issue's acceptance criteria, definition of done, and non-goals. - agent-station spec: "each acceptance criterion map to at least one scenario in a plan file"; re-running QA updates the same comment — [agent-station #14](https://github.com/ABilenduke/agent-station/issues/14)
- Linear-agent writing guidance for AI-ready issues; Copilot starts agent sessions from Linear issues and opens draft PRs — [junctionpanel write-linear-issues](https://junctionpanel.dev/blog/write-linear-issues-ready-for-ai-agent-automation/); [codeongrass Linear+Copilot](https://codeongrass.com/blog/linear-agents-github-copilot-draft-prs/)

## KQ6. Mapping a code diff to affected UI screens/flows (impact analysis)

### Takeaway
Three families are in use: (1) bundler/dependency-graph tracing from changed files to stories/components (Chromatic TurboSnap; Greptile/CodeRabbit code graphs; Richter symbol graph); (2) runtime coverage mapping of recorded user flows to lines (Meticulous curates sessions by which code paths they exercise); (3) LLM reading the diff to name routes/screens/journeys (Momentic explore, TesterArmy, mobile-pr-reviewer, pr-qa-copilot's static Next.js route detection, Claude skills). No tool documents an end-to-end "file → mobile screen → user flow" map; Revyl's Atlas/App Explorer graph and Figma-frame→screen config mapping are the nearest mobile primitives.

- pr-qa-copilot `auto_paths`: detects changed static Next.js routes from the diff — [pr-qa-copilot](https://github.com/ACHultman/pr-qa-copilot)

## KQ7. Handling PRs with insufficient context

### Takeaway
Documented strategies: skip with a neutral status when nothing is user-visible (TesterArmy "Tests skipped"); refuse to invent tests not grounded in the diff (QA.tech); fall back to exploration of the whole surface (TestSprite, TesterArmy predefined groups vs exploration mode); rely on repo-level instructions (CLAUDE.md "Demo hint", `.agents/skills/`, AGENTS.md) and project memory/test accounts; ask the user when ambiguous (Revyl cross-platform skill "asks which apps to compare"); create a ticket when none exists (Qodo+monday). No tool was found that posts a clarification request on the PR when AC are missing.

### Cited Findings
- TesterArmy: "If a change has no user-visible effect, the agent skips execution and reports a neutral 'Tests skipped' status"; planner uses "project memory, test accounts, and uploaded files" — [docs.tester.army](https://docs.tester.army/run/pr-exploration-agent)

- mobile-pr-reviewer: quality "depends on the 'Demo hint' in CLAUDE.md"; no pre-written plan, Claude is the planner — [mobile-pr-reviewer](https://github.com/RevylAI/mobile-pr-reviewer)

- Shiplight verify: skip for backend-only/docs-only changes — [skills.sh shiplight verify](https://www.skills.sh/shiplightai/claude-code-plugin/verify)

- Revyl cross-platform skill: "If the pairing isn't clear, it asks which apps to compare" — [cross-platform-review.md](https://github.com/RevylAI/revyl-cli/blob/main/docs/cross-platform-review.md)

### Inferences
- A verifier should emit a 3-way outcome (verified / not verifiable: skipped with reason / failed) plus a "context quality" note (AC found? PR template test-plan found?) and, when AC missing, fall back to diff-derived exploratory checks of affected screens while asking the author for AC via comment — this combination is not implemented by any surveyed tool.

## KQ8. Reported real-world results and failure modes (false positives/negatives, cost, run time)

### Takeaway
Hard numbers are scarce and mostly vendor-reported: Anthropic Code Review ~$15–25 and ~20 min per review, substantive comments 16%→54%; Bugbot ~90 s/review, resolution 52%→70%+; Greptile TREX +20% bugs in evals; Checksum ~70% failures auto-resolved; cubic cut false positives 51%; QA Wolf uses concurrency slots/queues. Failure modes documented by Cognition: agent over-tests unrelated areas, hallucinates non-existent app paths, misreports results unless forced to pre-declare expectations. Flakiness and trust erosion from red builds are the main CI-level risks cited. No Hacker News thread on agentic PR verification was found.

### Inferences
- Expect per-PR cost in the tens of dollars and 5–20+ minutes wall time for a browser/device-driving verifier with a frontier model (Anthropic's review alone is $15–25/20 min without a browser); mobile adds build + device boot time. Design levers: skip non-UI PRs, incremental re-verification on `synchronize`, effort tiers (Bugbot pattern), caps/budgets per repo.
- Trust depends on evidence (screenshots/video/trace per step) and on separating "verified failed" from "could not verify"; model self-reports are not acceptable as verdicts.

### Gaps
- No independent measurements of false-positive/negative rates for agentic UI verification; no HN/first-hand production reports found; no mobile-specific metrics.

## KQ9. GitHub mechanics for reporting verification results (Checks API, statuses, review comments, media, permissions, forks)

### Takeaway
A verifier can report via (a) Checks API check runs (`checks:write`; `output.title/summary/text` with Markdown, `summary`/`text` ≤ 65,535 chars, `annotations` ≤ 50 per request and appended across updates, `images[]` with `alt`, `image_url`, optional `caption`; usable as required checks), (b) commit statuses, (c) PR reviews/comments (idempotent single comment is the dominant pattern). Media: there is no official API to upload issue/PR attachments; options are check-run `images` with externally hosted URLs, release assets, an orphan branch, hosted services (Argos Media Sharing, Revyl recording links), or fragile cookie-based tools. `GITHUB_TOKEN` cannot attach a check run to a specific check suite and is read-only (no secrets) on fork `pull_request` runs; `pull_request_target` or a GitHub App installation token is the workaround.

### Cited Findings
- Checks API `output`: `title`, `summary` (Markdown, max 65,535), `text` (Markdown, max 65,535); `annotations` ("attach your analysis to specific lines of code and show in the Checks and Files changed tabs"; fields `path`, `start_line`, `end_line`, `annotation_level`, `message`, optional `title` ≤255, `raw_details` ≤64 KB, `start_column`/`end_column` same line only; max 50 per request, additional via Update endpoint, appended); `images` ("Properties of the images items: alt (string) Required... image_url (string) Required. The full URL of the image", caption optional); "Your GitHub App must have the checks:write permission to create check runs"; "to create a check run, you must use a GitHub App"; fork pushes "return an empty pull_requests array". — [GitHub REST checks/runs (GHES 3.13 mirror)](https://docs.github.com/en/enterprise-server@3.13/rest/checks/runs); [GHES 3.0 reference](https://docs.github.com/en/enterprise-server@3.0/rest/reference/checks); [current docs (not fetchable here)](https://docs.github.com/en/rest/checks/runs?apiVersion=2022-11-28)
- GitHub Support (community thread): "it is not currently possible to create a check run associated with a particular check suite with the GitHub Actions-provided GITHUB_TOKEN"; Sematext workaround: private GitHub App impersonated by a helper action with Checks read/write + Contents read. — [github.community thread](https://github.community/t/specify-check-suite-when-creating-a-checkrun/118380); [Sematext check run fix](https://sematext.com/docs/synthetics/ci-cd/ci-cd-check-run-fix/)
- Actions limits: a check suite can hold max 50,000 check runs. — [docs.github.com actions limits](https://docs.github.com/en/enterprise-server@3.22/actions/reference/limits)
- `GITHUB_TOKEN` on fork PRs: "if the workflow was triggered by a pull request from a forked repository, and the Send write tokens to workflows from pull requests setting is not selected, the permissions are adjusted to change any write permissions to read only"; secrets unavailable; `pull_request_target` grants read/write "even when it is triggered from a public fork". — [GITHUB_TOKEN reference (GHES 3.13)](https://docs.github.com/fr/enterprise-server@3.13/actions/reference/github_token-reference); [automatic token authentication](https://docs.github.com/ru/enterprise-server@3.8/actions/security-guides/automatic-token-authentication); [external-secrets/ok-to-test](https://github.com/external-secrets/ok-to-test)
- Maestro Cloud requires installing its GitHub App for "write access to PR statuses" and uses `pull_request_target` for forks with explicit HEAD checkout. — [docs.maestro.dev](https://docs.maestro.dev/maestro-cloud/ci-cd-integration/pull-request-integration)

- pr-qa-copilot: `deployments: read` to find preview URL via Deployments API; idempotent comment; artifacts via `actions: write`. — [pr-qa-copilot](https://github.com/ACHultman/pr-qa-copilot)
- Media upload: "GitHub doesn't provide an official API for comment attachments on issues and pull requests" (gh-attach; strategies: release-asset via documented API, browser-session cookies default; videos as bare URLs render inline); gh-image reads `user_session` cookie, uses internal asset endpoints returning `user-attachments` URLs, cookies expire; Playwright-driven comment-box file input trick; orphan-branch blob URLs; one unverified claim of `gh pr comment --attach` in gh 2.99+. — [Addono/gh-attach](https://github.com/Addono/gh-attach/); [drogers0/gh-image](https://github.com/drogers0/gh-image); [tonkotsuboy github-upload-image-to-pr](https://cdn.jsdelivr.net/gh/tonkotsuboy/github-upload-image-to-pr@main/README.md); [awesome-copilot pr-screenshots SKILL.md](https://git.cynarski.dev/Awesome/awesome-copilot/src/branch/main/skills/pr-screenshots/SKILL.md)

### Inferences
- Recommended reporting stack for a verifier: a GitHub App (not `GITHUB_TOKEN`) creating one check run per PR head SHA (`status: in_progress → completed`, `conclusion: success|failure|neutral|action_required`, `neutral` for "not verifiable/skipped"), `output.summary` with per-AC table, `output.images[]` pointing at externally hosted screenshots (S3/Revyl/Argos), plus one idempotent PR comment with the same table and video/recording links for mobile; annotations only if a failure maps to specific lines. Mark the check as required in branch protection for gating.
- For forks, run on `pull_request_target` with explicit head checkout (Maestro pattern) or require label-gated runs (`ok-to-test`).

- Could not fetch current (2022-11-28) docs.github.com page; limits quoted from GHES mirrors (likely identical but unverified). `gh pr comment --attach` unverified.

## Cross-cutting summary of what is missing (for the report writer)
1. No open-source project combines ticket/AC ingestion + diff impact analysis + agentic app driving + structured, evidence-rich GitHub check run. Each piece exists separately (Qodo/Augment for AC; TurboSnap/Meticulous for impact; mobile-pr-reviewer/Shiplight//verify/Copilot/Devin for driving; pr-qa-copilot/Momentic for GitHub plumbing).
2. Mobile is especially underserved: Revyl (and its tiny MIT demo) is the only agentic device loop; Maestro Cloud is scripted flows; no product documents AC→device test plan→evidence for iOS/Android.
3. No published, independent accuracy or cost benchmarks for agentic UI verification; vendor claims only; Cognition's blog is the only candid failure-mode write-up.
4. GitHub has no official media-attachment API; every tool uses external hosting or hacks. Check-run `images[]` with external URLs is the only first-class way to show screenshots in a check.
